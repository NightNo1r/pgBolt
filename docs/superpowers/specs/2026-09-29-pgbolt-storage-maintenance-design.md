# PgBolt — часть 2: Storage maintenance

Статус: одобрено ревью (5 итераций), реализовано (ред. 6; план docs/superpowers/plans/2026-09-29-pgbolt-storage-maintenance.md) · Дата: 2026-09-29 · Карта проекта: `2026-09-26-pgbolt-roadmap.md` · Основа: `2026-09-26-pgbolt-core-design.md` (далее «core»), `2026-09-28-pgbolt-worker-design.md` (далее «worker»)

## 1. Цель и рамки

Развёртывание PgBolt работает неограниченно долго без ручного обслуживания: партиции `jobs`/`job_events` всегда созданы вперёд, объём хранилища ограничен сроком retention и объёмом живых задач, строки упавших серверов убираются. Всё — безопасно при нескольких подах, через PgBouncer в transaction mode, без нарушения контракта HOT (core §4.2) и без долгих блокировок горячего пути.

**Входит:**
- периодический вызов `EnsurePartitionsAsync` (сама операция — core §4.4);
- retention: удаление партиций `jobs` и `job_events`; компактирование партиций `jobs`, которые держат живые задачи (живые строки переносятся в новую партицию тех же суток, старая удаляется);
- уборка строк `servers` упавших серверов;
- кластерная координация периодических задач (таблица `maintenance_tasks`);
- расписание в `PgBolt.Server` и ручной режим для core-only развёртываний;
- изменения core и worker, которых требует обслуживание (§9): уточнение протокола удаления партиции, самовосстановление строки `servers`, проверка версии схемы.

**Не входит (перенесено, roadmap обновляется):**
- opt-in индексы по `args` — часть 6 (Dashboard), где появляется спрос на выборки;
- тонкая настройка autovacuum `queue`, мониторинг bloat, оценка bulk enqueue через `COPY` против `unnest`, влияние числа присоединённых партиций на dequeue — часть 7 (нужны нагрузочный стенд и метрики).

Проверка горизонта при старте уже реализована в core (`PgBoltInitializer`, core §4.4): старт падает без партиций на текущие сутки, будущие создаются фоновым повтором. Часть 2 добавляет к ней только предупреждение о конфигурации (§6.4).

### Критерии успеха
- Партиции на текущие сутки существуют всегда, пока работает хотя бы один процесс с `RunMaintenance = true`; одиночная неудачная итерация не приводит к отсутствию партиции.
- Ни одна незавершённая задача (Pending: Scheduled / Enqueued / Processing; в части 5 — Awaiting) не удаляется retention'ом, сколько бы она ни ждала.
- Терминальные задачи (Succeeded, Failed, Cancelled) удаляются не раньше, чем через `JobsRetention` от суток их создания (UTC).
- Диск: партиции старше срока без живых задач удаляются целиком; партиция, закреплённая не более чем `RetentionCompactionMaxLiveJobs` живыми задачами, после компактирования занимает объём только своих живых строк (сжимается, когда терминальных строк не меньше `max(живых, 100)`, §5.3). Партиция с большим числом живых задач, а также любая закреплённая партиция, если `jobs` входит в публикацию логической репликации, не сжимается и занимает диск целиком до ухода живых задач — Warning при просрочке от 7 суток (§8). Число присоединённых партиций сверху не ограничено (закреплённые живут до ухода живых задач) — Warning при превышении штатного числа (§5.3, «Число партиций»).
- Пауза горячего пути от одной транзакции retention = ожидание блокировки родителя (не дольше `RetentionLockTimeout`, по умолчанию 100 мс) + удержание: statement'ы под блокировкой, паузы между round-trip'ами и `COMMIT`. Statement'ы и паузы **жёстко ограничены** таймаутами сервера, выставленными сразу после `LOCK` (при срабатывании транзакция откатывается); `COMMIT` (сброс WAL, ожидание синхронной реплики) не ограничен, но при зависшей синхронной реплике или диске WAL горячий путь стоит в любом случае (§5.3 п. 5). Штатно: `DETACH` группы до `K = 10` партиций — миллисекунды; компактирование одной партиции — пропорционально числу её живых строк (при 1000 — единицы-десятки мс). Файлы удаляются отдельными транзакциями без блокировки родителя. Держатель отсоединяемой партиции в обход родителя (autovacuum, прямой запрос) добавляет до `RetentionLockTimeout`; предпроверка `pg_locks` откладывает такие партиции заранее, но не гарантированно.
- После неудачной попытки (`lock_timeout` или срабатывание таймаута удержания) следующая попытка по той же таблице — не раньше следующего запуска retention, т. е. через `RetentionInterval`; в кластере запуски не выполняются параллельно несколькими подами (кроме безвредного перекрытия после паузы или падения пода, §6.2).
- Строка `servers` живого сервера, удалённая уборкой (пауза процесса или сети дольше `DeadServerTimeout`), восстанавливается следующим успешным heartbeat (§9.2).
- Результат не зависит от часового пояса сессии PostgreSQL.

## 2. Принятые решения

| Вопрос | Решение | Причина |
|---|---|---|
| Где выполняется периодическое обслуживание | В `PgBolt.Server`: третий цикл `housekeeping` в `ProcessingMaintenance` под существующим `RunMaintenance`. Операции — публичные в core (`IPgBoltMaintenance`) | Где воркеры, там и обслуживание; поды, только ставящие задачи, не делают служебных опросов. Core-only развёртывание вызывает операции из своего планировщика (§7) |
| Координация между подами | Таблица `maintenance_tasks` (строка на задачу, `next_run_at`); под захватывает задачу одним upsert `INSERT … ON CONFLICT (name) DO UPDATE … WHERE next_run_at <= now() RETURNING` | Работает через PgBouncer, без лидера и session state; интервал кластерный, а не на под; отсутствующая строка создаётся первым захватом. `pg_try_advisory_xact_lock` не держится между транзакциями (retention — несколько транзакций) и не убирает повтор работы каждым подом; «только jitter» умножает паузы горячего пути от `LOCK` на число подов |
| Отсчёт retention | От суток **создания** задачи (партиция `jobs` = сутки UUIDv7), на уровне партиций | Retention от `finished_at` требует seq scan всей суточной партиции перед удалением (индекса по `finished_at` нет и не будет — контракт HOT): десятки ГБ чтения на партицию. Цена решения: долго ждавшая или ретраившаяся задача после завершения хранится меньше `JobsRetention` (§5.3) |
| Что удаляет retention | Только терминальные задачи. Партиция с живыми задачами не удаляется; при числе живых не больше `RetentionCompactionMaxLiveJobs` она **компактируется**: под блокировкой родителя старая партиция отсоединяется, живые строки переносятся в новую партицию тех же суток, старая таблица с терминальными строками удаляется | Контракт core §4.4. Живая задача может ждать сколько угодно. Закрепление — обычная ситуация, а не редкость: `Delay`/`RunAt` дальше `Rd`, очередь без потребителя, долгие ретраи. Построчный `DELETE` место не возвращает (новые строки в прошлую партицию не пишутся, файл не уменьшается), пишет WAL на каждую строку и требует бюджета и курсора; компактирование возвращает место одной короткой транзакцией, пауза горячего пути пропорциональна числу живых строк и ограничена порогом. Цена: компактирование, как `TRUNCATE`, не MVCC-безопасно для снимков REPEATABLE READ/SERIALIZABLE, взятых до него (§5.3); горячий путь (READ COMMITTED) не затронут. При публикации `jobs` в логической репликации компактирование пропускается |
| Блокировки при удалении и компактировании | `LOCK TABLE ONLY` на родителе; группа до `K = 10` отсоединяемых партиций под одной блокировкой, компактирование — одна партиция на транзакцию. Под блокировкой три round-trip'а (пакет А: `LOCK` и проверка; пакет Б: DDL; `COMMIT`), statement'ы и паузы ограничены `SET LOCAL statement_timeout` и `idle_in_transaction_session_timeout`. `DROP TABLE` — отдельной транзакцией на таблицу (§5.3, §9.1) | Без `ONLY` блокировка рекурсирует на все партиции: autovacuum (`SHARE UPDATE EXCLUSIVE`) на сегодняшних партициях при `lock_timeout` 100 мс не отменяется (отмена autovacuum — после `deadlock_timeout`, 1 с), и почти каждая попытка — `LockTimeout` с остановкой горячего пути. `DROP` на коммите удаляет файлы и вычищает буферы партиции из `shared_buffers` до освобождения блокировок — сотни мс под блокировкой родителя для партиции в десятки ГБ. Группа: первый запуск после обновления обрабатывает сотни партиций, по транзакции на каждую — сотни остановок горячего пути подряд; компактирование по одной — чтобы удержание не складывалось из нескольких переносов. Каждый round-trip под `ACCESS EXCLUSIVE` добавляет RTT и паузу клиента (GC), поэтому их минимум, а серверные таймауты ограничивают их независимо от клиента. `DETACH … CONCURRENTLY` не выполняется в блоке транзакции (нет перепроверки под блокировкой) и ждёт все транзакции, видевшие родителя |
| `LockTimeout` и таймаут удержания в retention | Не ошибка задачи: `Deferred(LockTimeout)` / `Deferred(HoldTimeout)`, `last_error` не пишется, `next_run_at` не сокращается, повтор — следующим запуском | Ускоренный повтор давал бы до 60 остановок горячего пути в час (core §4.4 требует ограничивать повторы). Систематическая проблема видна по Warning (§8) |
| Раздельный retention | `JobsRetention` и `EventsRetention`, независимые, по умолчанию 7 суток, `null` = хранить вечно (задаётся только кодом, §5.1) | События — отладочный журнал, их часто хотят хранить меньше (или больше) |
| Сроки по состояниям (как в Hangfire) | Не делаем | Требует построчных `DELETE` по `state` без индекса: WAL, bloat, полные сканы |
| Порог уборки `servers` | Настройка `DeadServerTimeout` (30 мин), не зависящая от `HeartbeatInterval` удалённых подов | Удаление строки живого сервера (пауза дольше порога) не влияет на lease: продление от строки `servers` не зависит (core §5.5). Heartbeat сообщает, что строки нет, и сервер регистрируется заново upsert'ом (§9.2); в dashboard сервер пропадает до следующего heartbeat |
| Метрики и алерты | Логи; метрики — часть 7 | OpenTelemetry-инструментирования пока нет |

## 3. Время и сутки

`now()` возвращает `timestamptz` — абсолютный момент; часовой пояс сессии влияет только на отображение и приведение к `date`/`timestamp`. Правила (обязательны для всего SQL части 2):

1. **Календарные сутки** (имя партиции, «сегодня», кандидаты retention) вычисляются только как `(now() AT TIME ZONE 'UTC')::date` — как в `PartitionManager.TodayAsync`. `now()::date` дал бы дату пояса сессии.
2. **Моменты времени** сравниваются только как `timestamptz` с `now()`: `heartbeat_at < now() - @timeout`, `next_run_at <= now()`. Выражение `now() AT TIME ZONE 'UTC'` имеет тип `timestamp without time zone`; сравнение его с `timestamptz` неявно приводит его обратно через пояс сессии и сдвигает результат на смещение пояса — запрещено.
3. Границы партиций `job_events` — литералы `timestamptz` с `+00`, границы `jobs` — `UuidV7.LowerBound(day)` (как сейчас в `PartitionManager`).

Все вычисления по суткам делает C# по значению `today` (тип `DateOnly`), полученному из БД в начале операции одним запросом.

## 4. Схема: миграция V002

```sql
CREATE TABLE {schema}.maintenance_tasks (
    name             text        PRIMARY KEY,
    next_run_at      timestamptz NOT NULL,
    last_run_at      timestamptz,          -- начало последнего захвата; токен владения запуском (§5.7)
    last_finished_at timestamptz,          -- завершение последнего запуска (Complete)
    last_error       text
);
```

- Файл `Schema/Migrations/V002__maintenance_tasks.sql`, применяется существующим `MigrationRunner` (core §4.7). `PgBoltMigrations.GetScript(schema, fromVersion: 1)` включает V002 автоматически.
- Строки задач миграция не вставляет: их создаёт первый захват (upsert, §5.7) — сразу при первом проходе цикла, поэтому первый поднявшийся под выполняет все задачи сразу. Задача без строки не «теряется» никогда; строка, удалённая вручную, создаётся заново. Будущие периодические задачи (например, часть 4) миграций для строк не требуют.
- Таблица крошечная (строка на задачу, обновление раз в минуты); настройки autovacuum по умолчанию.
- V002 аддитивна: существующие таблицы не меняются, код без части 2 на схеме V002 работает без изменений (порядок раскатки — §10).

**Проверка версии схемы** (изменение core §4.7, §9.3): код знает версии до `LatestVersion`; версия БД **новее** кода — не ошибка, а Warning при старте (схема поднята более новым релизом при rolling deploy, миграции аддитивны в пределах мажорной версии). Ошибка — только `version < LatestVersion` при `AutoMigrate = false`. `EnsurePartitionsAsync` вызывает `MigrateAsync` только при `AutoMigrate && (version is null || version < LatestVersion)` (`null` — схемы или `schema_version` нет; сейчас — при `!=`, что на более новой схеме давало холостой `MigrateAsync` с `CREATE SCHEMA IF NOT EXISTS` каждый час).

## 5. Операции core (`PgBolt.Postgres`)

### 5.1 API

```csharp
/// <summary>Обслуживание схемы (§4.4 core, часть 2). Все операции идемпотентны и безопасны при параллельном вызове.</summary>
public interface IPgBoltMaintenance
{
    /// <param name="daysAhead">null — PgBoltOptions.PartitionDaysAhead.</param>
    Task<PartitionEnsureResult> EnsurePartitionsAsync(int? daysAhead = null, CancellationToken ct = default);

    Task<RetentionResult> ApplyRetentionAsync(CancellationToken ct = default);

    Task<int> RemoveDeadServersAsync(TimeSpan olderThan, CancellationToken ct = default);
}

public sealed record RetentionResult(
    IReadOnlyList<DateOnly> DroppedJobsPartitions,    // удалены целиком, включая отсоединённые прошлыми запусками
    IReadOnlyList<DateOnly> DroppedEventsPartitions,
    int DroppedCompactionRemnants,                    // удалены остатки компактирования прошлых запусков (§5.2), без остатков этого запуска
    IReadOnlyList<PinnedPartition> Pinned,            // закреплены живыми задачами, не больше порога
    IReadOnlyList<DeferredPartition> Deferred,
    int AttachedJobsPartitions);                      // присоединённых партиций jobs после запуска (§5.3, «Число партиций»)

public sealed record PinnedPartition(DateOnly Day, int OverdueDays, int LiveJobs, bool Compacted);

public sealed record DeferredPartition(string Table, DateOnly Day, DeferReason Reason, int OverdueDays, int? LiveJobs,
    string? Error = null);                            // текст исключения — только для DropFailed

public enum DeferReason { LockTimeout, HoldTimeout, DropLockTimeout, DropFailed, LiveJobs, Replicated }
```

- `OverdueDays` — на сколько суток кандидат просрочен относительно своей границы удаления (0 — стал кандидатом в текущие сутки; для остатков при `Retention = null` — 0). Используется вызывающим для предупреждений (§8); core не пишет логов из этих операций.
- `DeferredPartition.Table` — `"jobs"` или `"job_events"`.
- `PinnedPartition`: `Compacted = true` — сжата в этом запуске; `false` — терминальных строк меньше `max(LiveJobs, 100)`, сжатие не окупает остановку горячего пути (§5.3 п. 1). `LiveJobs` — число живых задач по предпроверке.
- Партиция, сжатая в этом запуске, попадает только в `Pinned(Compacted = true)`; её остаток `jobs_D_r<oid>`, удалённый транзакцией 2 того же запуска, в `DroppedCompactionRemnants` не считается (там — только остатки прошлых запусков). Если `DROP` этого остатка получил `DropLockTimeout` (или `DropFailed`), партиция дополнительно попадает в `Deferred` с этой причиной — одни и те же сутки в `Pinned` и `Deferred` одновременно допустимы и нормальны: сжатие выполнено, удаление остатка отложено.
- `LockTimeout` — партиции остались присоединёнными и не изменились. Источники: `55P03` в предпроверке п. 1 и в прогреве п. 4 (эта партиция), находка предпроверки `pg_locks` п. 3 (эта партиция), `55P03` на `LOCK` родителя или `DETACH` в транзакции 1 п. 5 (все партиции группы). Отложения до `LOCK` родителя (п. 1, п. 3, п. 4) остановку обработки не вызывают; останавливает только `LockTimeout` транзакции 1 (п. 2). `HoldTimeout` — под блокировкой родителя сработал `statement_timeout` или `idle_in_transaction_session_timeout` (§5.3 п. 5); транзакция откатилась, все партиции группы не изменились. `DropLockTimeout` — таблица отсоединена, но `DROP` не получил блокировку; горячий путь её уже не видит, она удаляется как остаток следующим запуском (§5.2). `DropFailed` — транзакция 2 этой таблицы упала с другой ошибкой (§5.3, «Обработка ошибок»); таблица, как и при `DropLockTimeout`, остаётся остатком для следующего запуска.
- `LiveJobs` — живых задач больше `RetentionCompactionMaxLiveJobs` (или компактирование выключено), партиция не сжимается и ждёт их ухода. `Replicated` — партицию нужно сжать, но `jobs` или её партиции входят в публикацию логической репликации (§5.3 п. 1), компактирование пропущено. Поле `LiveJobs` — только для этих двух причин: число живых задач по предпроверке с `LIMIT T + 1` (значение `T + 1` означает «больше `T`»); для остальных причин `null`.
- Кандидаты, до которых обработка не дошла из-за остановки после `LockTimeout`/`HoldTimeout` (§5.3 п. 2), в `Pinned`/`Deferred` не попадают — при остановке на этапе отсоединения это в том числе все компактирования; итоги предпроверки п. 1 (`Pinned(Compacted = false)`, `Deferred(LiveJobs)`, `Deferred(Replicated)`, `Deferred(LockTimeout)` из п. 1) попадают всегда.
- `AttachedJobsPartitions` — отдельный запрос в конце операции: `SELECT count(*) FROM pg_inherits WHERE inhparent = '{schema}.jobs'::regclass`.
- `EnsurePartitionsAsync(int? daysAhead = null)` — изменение публичного API core (сейчас `int daysAhead = 7`, игнорирующее `PgBoltOptions.PartitionDaysAhead`); до 1.0 допустимо, вызовы с явным `int` компилируются без изменений (breaking changes — §10).

Новые настройки `PgBoltOptions`:

| Настройка | По умолчанию | Валидация |
|---|---|---|
| `JobsRetention` (`TimeSpan?`) | 7 суток | `null` или `> 0` и `≤ 3650 суток` |
| `EventsRetention` (`TimeSpan?`) | 7 суток | `null` или `> 0` и `≤ 3650 суток` |
| `RetentionLockTimeout` (`TimeSpan`) | 100 мс | `> 0` и `≤ 1 мин` |
| `RetentionCompactionMaxLiveJobs` (`int`) | 1000 | `≥ 0` и `≤ 10 000`; `0` — компактирование выключено |

- Retention округляется вверх до целых суток: `Rd = ceil(Retention / 1 сутки)`; минимальный эффективный срок — 1 сутки. Верхние границы исключают переполнение `DateOnly.AddDays` и миллисекунд `lock_timeout` в `int`; `lock_timeout` дольше минуты противоречит смыслу настройки. Обоснование порога компактирования и его верхней границы — §5.3, «Порог».
- XML-doc `RetentionCompactionMaxLiveJobs`: компактирование не MVCC-безопасно для снимков REPEATABLE READ/SERIALIZABLE (§5.3, «MVCC»; READ COMMITTED не затронут) — если отчёты или выгрузки читают `jobs` в REPEATABLE READ, порог нужно выставить в `0`; при публикации `jobs` в логической репликации компактирование пропускается (`Deferred(Replicated)`).
- **Отключение retention — только кодом:** `o.JobsRetention = null` / `o.EventsRetention = null`. Из `IConfiguration` значение `null` однозначно не задаётся (пустая строка и отсутствие ключа у разных провайдеров и версий binder'а ведут себя по-разному), поэтому отсутствие ключа всегда означает значение по умолчанию. Фиксируется в XML-doc.
- XML-doc `JobsRetention`/`EventsRetention`: первый запуск retention после обновления удаляет все партиции старше срока (§10); партиция, закреплённая живыми задачами, после компактирования занимает объём живых строк, а при числе живых больше `RetentionCompactionMaxLiveJobs` — диск целиком до их ухода (§5.3); при `null` число партиций растёт на одну в сутки без ограничения (§5.3, «Число партиций»). Настройки retention (и порог компактирования) должны совпадать на всех подах и приложениях одной схемы: запуск выполняет тот под, который захватил задачу, поэтому фактически действует самый короткий срок среди процессов, выполняющих обслуживание.

### 5.2 Кандидаты retention и имена таблиц

Партиция суток `D` — кандидат, если `D ≤ today − 1 − Rd`, т. е. её верхняя граница `D + 1` плюс срок не позже начала текущих суток UTC. Пример: `Rd = 7`, `today = 2026-10-10` → кандидаты `D ≤ 2026-10-02`; партиция 2026-10-02 закрыта 2026-10-03 00:00 UTC, срок истёк 2026-10-10 00:00 UTC. Сегодняшняя и будущие партиции кандидатами не бывают никогда.

`OverdueDays = (today − 1 − Rd) − D`.

Список — одним запросом, присоединённые партиции и отсоединённые таблицы вместе:

```sql
SELECT c.oid::bigint AS oid, c.relname,
       CASE i.inhparent WHEN '{schema}.jobs'::regclass       THEN 'jobs'
                        WHEN '{schema}.job_events'::regclass THEN 'job_events'
                        ELSE i.inhparent::oid::text END AS parent  -- NULL → отсоединена
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
LEFT JOIN pg_inherits i ON i.inhrelid = c.oid
WHERE n.nspname = @schema AND c.relkind = 'r'
  AND c.relname ~ '^(jobs_[0-9]{8}(_r[0-9]+)?|job_events_[0-9]{8})$';
```

Чужой родитель выводится числом `oid`, а не `regclass::text`: тот выводит имя без схемы, если таблица видна через `search_path`, и партиция чужого `other.jobs` получила бы родителя `jobs`.

Имя разбирается строгим regex `^jobs_(\d{8})(?:_r(\d{1,10}))?$` или `^job_events_(\d{8})$` и `DateOnly.TryParseExact("yyyyMMdd")`; неразобранная дата — пропуск. `<oid>` в имени остатка — `oid` прежней партиции (уникален среди существующих таблиц, поэтому имена остатков не совпадают):

| Имя | Родитель | Что это | Действие |
|---|---|---|---|
| `jobs_D`, `job_events_D` | `jobs` / `job_events` соответственно | партиция | кандидат по правилу суток |
| `jobs_D`, `job_events_D` | нет | остаток `DETACH`: отсоединена, `DROP` не выполнен | удалить (транзакция 2) |
| `jobs_D_r<oid>` | нет | остаток компактирования: прежняя партиция, отсоединена и переименована | удалить (транзакция 2) |
| прочее (чужой родитель, `jobs_D_r<oid>` присоединённая, другое имя) | — | не наша таблица | не трогать, в результат не попадает |

- Границы партиции через `pg_get_expr` не сверяются: таблицы с такими именами в схеме создаёт только PgBolt (фиксируется в XML-doc: для архивирования партицию нужно переименовать или перенести в другую схему).
- **Остатки** — след прерванной обработки: транзакция 1 (`DETACH` или компактирование) закоммичена, `DROP` не выполнен (падение пода между транзакциями 1 и 2, `DropLockTimeout`). Транзакция 1 атомарна, поэтому других промежуточных состояний нет. Остаток удаляется **при любом значении retention** (включая `null`) и без проверок задач: решение принято при `DETACH`, горячий путь его не видит, живых задач в нём нет (проверено под блокировкой; живые строки остатка компактирования — копии, оригиналы в новой партиции). Единственная проверка — в транзакции 2 перед `DROP` (§5.3 п. 6). Остатки удаляются первыми (§5.5).
- **`oid` на стороне клиента — `long`.** Читается как `c.oid::bigint`, передаётся параметрами `bigint`/`bigint[]` с приведением `::oid` / `::oid[]` в тексте SQL (§5.3, §5.4): так код не зависит от поддержки `uint`/`oid[]` в `NpgsqlSlimDataSourceBuilder`.
- `oid` из списка — идентичность таблицы на весь запуск: транзакция 1 проверяет присоединённость по нему, транзакция 2 удаляет таблицу, только если имя по-прежнему указывает на этот `oid`. `DETACH` и `RENAME` `oid` не меняют; новая партиция компактирования получает новый `oid`.

`EnsurePartitionsAsync` создаёт и присоединяет партиции только от `today` вперёд, поэтому удалённые прошлые партиции не создаются заново, а прошлая таблица не становится снова присоединённой. Единственное присоединение прошлых суток — новая таблица компактирования вместо отсоединённой в той же транзакции партиции тех же суток (§5.3).

### 5.3 Retention `jobs`

`@lo = UuidV7.LowerBound(D)`, `@hi = UuidV7.LowerBound(D + 1)`, `@oid` и `@rel` (`'{schema}.jobs_YYYYMMDD'`) — из списка §5.2, `T = RetentionCompactionMaxLiveJobs`, `@limit = T + 1`. Внутренние параметры — поля `internal sealed record RetentionTuning`, который `PgBoltMaintenance` получает через internal-конструктор/DI (по умолчанию — `RetentionTuning.Default`): `K = 10` (`PartitionsPerTransaction`), `HoldStatementTimeout = 2 с`, `HoldIdleTimeout = 1 с`; тесты создают свой экземпляр, глобального изменяемого состояния нет. `MinCompactionGain = 100` — константа.

Термины: **группа** — до `K` партиций, обрабатываемых одной транзакцией 1 под одной блокировкой родителя (компактируемая партиция — всегда группа из одной); **пакет А/Б** — `NpgsqlBatch` транзакции 1 (п. 5).

**1. Предпроверка** каждого присоединённого кандидата — без блокировок горячего пути, **отдельной короткой транзакцией на каждую партицию** с `SET LOCAL lock_timeout = '<RetentionLockTimeout>ms'` (только запросы этой партиции, коммит сразу после них; общей транзакции на все кандидаты нет, остальные запросы запуска вне транзакций 1 и 2 — autocommit): `55P03` одной партиции не прерывает предпроверку остальных, а `ACCESS SHARE` на прочитанных партициях не копятся до конца общей транзакции:

```sql
SELECT to_regclass(@rel) = @oid::oid;                          -- имя указывает на oid из списка §5.2
SELECT job_id FROM {schema}.queue
WHERE job_id >= @lo AND job_id < @hi LIMIT @limit;           -- живые (Pending ⇔ строка в queue, core §4.4)
```
- Сверка `oid` не `true` (таблица удалена или заменена другим подом — например, сжата, и имя указывает на новую партицию) → пропуск, в результат не попадает; к партиции по имени предпроверка не обращается. Обе команды — одним пакетом после `SET LOCAL lock_timeout`.
- 0 строк → партиция **отсоединяется**.
- `L = 1..T` строк → окупится ли сжатие: `SELECT count(*) FROM (SELECT 1 FROM {schema}.jobs_YYYYMMDD LIMIT @l + @g) x`, где `g = max(L, MinCompactionGain)`. Каждой строке `queue` соответствует строка `jobs`, поэтому `count = L + g` ⇔ терминальных строк не меньше `g`; seq scan останавливается на `L + g`-й строке. Терминальных меньше → `Pinned(Compacted = false)`, партиция не трогается: сжатие уменьшило бы её меньше чем вдвое (или меньше чем на 100 строк) ценой остановки горячего пути, а без порога сжатая партиция сжималась бы заново каждым запуском после каждого ack. Иначе партиция **компактируется**; массив её живых id сохраняется для прогрева (п. 4). Тем же пакетом после `count` сверка `oid` **повторяется**: `count` обращается к партиции по имени, и если он ждал блокировку старой таблицы (её держала транзакция 1 другого пода, сжимающего партицию, — окно до `RetentionLockTimeout`), то после получения блокировки PostgreSQL заново разрешает имя и читает уже новую таблицу. Прочитанная таблица до конца транзакции под `ACCESS SHARE` (её не переименовать и не удалить), поэтому повторная сверка `true` ⇔ прочитана таблица из списка; не `true` → пропуск, в результат не попадает. Предварительная сверка остаётся: она дешёвая и избавляет от скана в обычном случае.
- `T + 1` строк (при `T = 0` — любая) → `Deferred(LiveJobs)` с `LiveJobs = T + 1`, партиция не трогается.

**Публикации.** Один раз за запуск, до компактирований:
```sql
SELECT EXISTS (SELECT 1 FROM pg_publication WHERE puballtables)
    OR EXISTS (SELECT 1 FROM pg_publication_tables
               WHERE schemaname = @schema AND tablename ~ '^jobs(_[0-9]{8})?$');
```
`true` → каждая партиция, которую нужно компактировать, получает `Deferred(Replicated)` с числом живых; отсоединение и `DROP` выполняются как обычно (DDL логической репликацией не передаётся). Причина: при `FOR ALL TABLES` (и `FOR TABLES IN SCHEMA`, PostgreSQL 15+) вставка живых строк в новую таблицу до её `ATTACH` публикуется как вставка в неизвестную подписчику таблицу — репликация останавливается с ошибкой, CDC-потребитель получает дубликаты; при публикации отдельной партиции новая таблица в публикацию не входит; при публикации `jobs` целиком перенос проходит мимо потока изменений. Поэтому компактирование пропускается при любой публикации, затрагивающей `jobs` (`pg_publication_tables` раскрывает публикации по таблицам и по схемам — родителя или партиции, в зависимости от `publish_via_partition_root`).

**2. Порядок и остановка.** Сначала отсоединяемые партиции — группами до `K`, затем компактируемые — по одной; внутри каждого вида — от старых к новым. Перед каждой транзакцией 1 — своя предпроверка `pg_locks` (п. 3), перед компактированием — ещё и свой прогрев (п. 4). После `COMMIT` каждая отсоединённая таблица удаляется своей транзакцией 2 (п. 6). `LockTimeout` или `HoldTimeout` в транзакции 1 относится ко **всем партициям группы**, и **остальные присоединённые кандидаты `jobs` в этом запуске не обрабатываются** (и в результат не попадают, §5.1): то, что помешало одной попытке (долгий запрос, медленный диск, пауза клиента), помешает и следующим, а каждая попытка ставит горячий путь в очередь. При остановке на этапе отсоединения компактирования в этом запуске не выполняются и в результат не попадают (кроме итогов предпроверки п. 1). Порядок от старых к новым гарантирует, что отложенная группа содержит самые просроченные партиции **среди отсоединяемых** (компактируемые идут после всех отсоединяемых, даже если они старше). Остатки и retention `job_events` (§5.4) при этом выполняются.

**3. Предпроверка `pg_locks`** непосредственно перед каждой транзакцией 1, по партициям её группы — один снимок `pg_locks` (каждое обращение к представлению строит новый):
```sql
WITH l AS MATERIALIZED (
    SELECT pid, virtualtransaction, relation FROM pg_locks
    WHERE locktype = 'relation' AND granted AND pid IS DISTINCT FROM pg_backend_pid()
      AND database = (SELECT oid FROM pg_database WHERE datname = current_database())
)
SELECT DISTINCT l.relation FROM l
WHERE l.relation = ANY(@partition_oids::bigint[]::oid[])
  AND NOT EXISTS (SELECT 1 FROM l p                          -- держит в обход родителя
                  WHERE (p.pid = l.pid OR p.virtualtransaction = l.virtualtransaction)
                    AND p.relation = '{schema}.jobs'::regclass);
```
Держатель сопоставляется по `pid` **или** `virtualtransaction`: у блокировок prepared-транзакций (2PC) `pid` — `NULL` (`pid <> …` их бы отбросило, а `p.pid = l.pid` для `NULL` не выполняется), `virtualtransaction` есть и уникален — для них срабатывает он. Одного `virtualtransaction` мало: `pg_locks` не даёт согласованного снимка (fast-path блокировки собираются раньше основной таблицы блокировок), и сеанс горячего пути между чтениями может сменить транзакцию — родитель попадёт со старым `virtualtransaction`, партиция с новым, и партиция ложно исключится (`Deferred`); совпадение `pid` это покрывает. Иначе партиция, которую держит prepared-транзакция, не исключалась бы заранее и каждый запуск упирался бы в `lock_timeout` всей группы.

Уровень блокировки партиции у не-`CONCURRENTLY` `DETACH` зависит от версии (в PostgreSQL 13 — возможно `SHARE UPDATE EXCLUSIVE`, в 14+ — `ACCESS EXCLUSIVE`), но последующие `RENAME` (компактирование) и `DROP` (транзакция 2) берут `ACCESS EXCLUSIVE` в любом случае, поэтому держатель любой блокировки партиции помешает её обработке. Предпроверка — эвристика, уменьшающая число остановок горячего пути; корректность на неё не опирается (держателя, пропущенного ею, ловит `lock_timeout`). Держатели, у которых есть и блокировка родителя (горячий путь: запросы без pruning, например join dequeue, блокируют все партиции), не учитываются — их дождётся `LOCK` родителя. Найденные партиции (autovacuum старой партиции, в том числе anti-wraparound, который не отменяется; прямой запрос к партиции) исключаются из группы → `Deferred(LockTimeout)` без остановки горячего пути. Проверка — снимок: держатель, появившийся после неё, ловится `lock_timeout` в `DETACH`.

**4. Прогрев** (только компактирование) — сразу после предпроверки `pg_locks` своей партиции, короткой транзакцией с тем же `lock_timeout`:
```sql
SELECT sum(octet_length(j::text)) FROM {schema}.jobs_YYYYMMDD j WHERE j.id = ANY(@ids);
```
`@ids` — живые id из предпроверки п. 1. Преобразование строки в текст читает все колонки и детоастит `args`, поэтому план — Index Scan (или Bitmap Heap Scan) по PK партиции с чтением heap и TOAST (`count(*)` дал бы Index Only Scan и не прочитал бы ни heap, ни TOAST). `INSERT … SELECT` под блокировкой (п. 5) читает те же страницы — после прогрева из `shared_buffers`. Прогрев — перед каждой транзакцией, а не в общей предпроверке, чтобы прогретые страницы не вытеснялись остальными транзакциями запуска. Задачи, появившиеся после предпроверки, не прогреты — их единицы.

**5. Транзакция 1.** Открывается `BeginTransactionAsync` (Npgsql отправляет `BEGIN` вместе с первой командой, без отдельного round-trip'а), закрывается `CommitAsync`; в тексте команд `BEGIN`/`COMMIT` нет, поэтому транзакция совместима и с multiplexing Npgsql. Под блокировкой родителя — три round-trip'а: пакет А, пакет Б, `COMMIT`. Если пакет Б не нужен — `RollbackAsync` сразу после пакета А. При ошибке и при отмене токеном — `RollbackAsync(CancellationToken.None)`, только если соединение открыто (`conn.FullState` без `Broken`/`Closed`); исключения самого отката глотаются (лог Debug). Если соединение уже разорвано, транзакцию откатил сервер, а Npgsql откатывает незавершённую транзакцию и при dispose транзакции/возврате соединения в пул.

Пакет А, общий префикс:
```sql
SET LOCAL lock_timeout = '<RetentionLockTimeout>ms';
LOCK TABLE ONLY {schema}.jobs IN ACCESS EXCLUSIVE MODE;           -- только родитель, без рекурсии на партиции
SET LOCAL statement_timeout = '<HoldStatementTimeout + RetentionLockTimeout>ms';
SET LOCAL idle_in_transaction_session_timeout = '<HoldIdleTimeout>ms';
-- + проверка (ниже)
```

*Отсоединение* (группа до `K` партиций), проверка — один запрос по всем партициям группы:
```sql
SELECT p.oid::bigint AS oid,
       to_regclass(p.rel) = p.oid
         AND EXISTS (SELECT 1 FROM pg_inherits i
                     WHERE i.inhrelid = p.oid AND i.inhparent = '{schema}.jobs'::regclass) AS attached,
       EXISTS (SELECT 1 FROM {schema}.queue q
               WHERE q.job_id >= p.lo AND q.job_id < p.hi) AS has_live   -- повтор под блокировкой
FROM unnest(@oids::bigint[]::oid[], @rels::text[], @los::uuid[], @his::uuid[]) AS p(oid, rel, lo, hi);
```
Пакет Б — `ALTER TABLE {schema}.jobs DETACH PARTITION {schema}.jobs_YYYYMMDD;` для каждой партиции с `attached AND NOT has_live`. `NOT attached` → пропуск (обработал другой под), таблица — в список транзакции 2 (удалится, только если отсоединена и имя указывает на тот же `oid`). `has_live` → партиция пропускается до следующего запуска (там она пройдёт предпроверку п. 1 заново), в результат не попадает. Отсоединять нечего → `RollbackAsync` вместо пакета Б.

*Компактирование* (одна партиция), проверка — один запрос:
```sql
SELECT to_regclass(@rel) = @oid::oid
         AND EXISTS (SELECT 1 FROM pg_inherits
                     WHERE inhrelid = @oid::oid AND inhparent = '{schema}.jobs'::regclass) AS attached,
       ARRAY(SELECT job_id FROM {schema}.queue
             WHERE job_id >= @lo AND job_id < @hi LIMIT @limit) AS ids;  -- повтор под блокировкой
```
По результату клиент выбирает пакет Б:
- `NOT attached` → `RollbackAsync`, пропуск (обработал другой под), таблица — в список транзакции 2 с той же оговоркой.
- `ids` пуст → отсоединение: пакет Б — `DETACH PARTITION`.
- в `ids` больше `T` → `RollbackAsync`, `Deferred(LiveJobs)`.
- иначе — компактирование, пакет Б:
```sql
ALTER TABLE {schema}.jobs DETACH PARTITION {schema}.jobs_YYYYMMDD;
ALTER TABLE {schema}.jobs_YYYYMMDD RENAME TO jobs_YYYYMMDD_r<oid>;  -- <oid> = @oid старой партиции
CREATE TABLE {schema}.jobs_YYYYMMDD
    (LIKE {schema}.jobs INCLUDING DEFAULTS INCLUDING CONSTRAINTS)
    WITH (fillfactor = <JobsFillFactor>);                         -- DDL как в PartitionManager
INSERT INTO {schema}.jobs_YYYYMMDD
SELECT * FROM {schema}.jobs_YYYYMMDD_r<oid> WHERE id = ANY(@ids);
ALTER TABLE {schema}.jobs ATTACH PARTITION {schema}.jobs_YYYYMMDD
    FOR VALUES FROM ('<lo>') TO ('<hi>');                         -- проверка границ сканирует ≤ T строк; индексы родителя строятся
```

- **`NpgsqlBatch`, а не `DO`-блок.** Пакет передаёт `@ids` параметром `uuid[]`; `DO` параметров не принимает (массив — литералом, DDL — через `EXECUTE format(...)`), а round-trip'а не экономит: результат проверки нужен клиенту до DDL. Имена и границы подставляются в текст из валидированной схемы (`SchemaName.Validate`), даты (`yyyyMMdd`) и `oid` (число), как в `PartitionManager`. Ошибка пакета приходит с `SQLSTATE` конкретной команды, остальные команды пакета сервер пропускает.
- **Таймауты удержания.** `SET LOCAL` — транзакционные: действуют до конца транзакции и не остаются на серверном соединении, поэтому безопасны в PgBouncer transaction mode (как `lock_timeout` в core); оба параметра — `USERSET`, допустимы в `SET LOCAL` на PostgreSQL 13+. Выставляются после `LOCK`, чтобы ожидание блокировки родителя ограничивал только `lock_timeout`. `statement_timeout` ограничивает каждый statement под блокировкой (в расширенном протоколе — каждый `Execute` пакета отдельно); к `HoldStatementTimeout` прибавлен `RetentionLockTimeout`, потому что `DETACH` может ждать блокировку партиции. `idle_in_transaction_session_timeout` ограничивает обе паузы — между пакетами А и Б и между пакетом Б и `COMMIT` (RTT и пауза клиента — GC, throttling): при срабатывании сервер завершает сеанс, транзакция откатывается; через PgBouncer клиент видит разрыв соединения, Npgsql выбрасывает соединение из пула.
- **Граница удержания.** Под блокировкой после `LOCK` выполняются: два `SET LOCAL` (мгновенны), проверка и пакет Б — `K` `DETACH` для группы, пять statement'ов для компактирования (`DETACH`, `RENAME`, `CREATE`, `INSERT`, `ATTACH`). Жёсткая граница без `COMMIT` — `n × (HoldStatementTimeout + RetentionLockTimeout) + 2 × HoldIdleTimeout`, где `n` — число statement'ов после `LOCK` (`3 + K` или 8). Практически от данных зависят только проверка, `INSERT` и `ATTACH` (каталожные DDL — константа, `DETACH` ждёт партицию не дольше `RetentionLockTimeout`): порядка `3 × HoldStatementTimeout + 2 × HoldIdleTimeout` (8 с) для компактирования и `HoldStatementTimeout + K × RetentionLockTimeout + 2 × HoldIdleTimeout` (≈ 5 с) для группы. Штатно — миллисекунды-десятки мс.
- **`COMMIT` не ограничен.** `statement_timeout` снимается до выполнения коммита, поэтому сброс WAL и ожидание синхронной реплики (`synchronous_commit` ≥ `on` при `synchronous_standby_names`) ограничены только самим сервером. Отдельного механизма нет и не нужно: WAL транзакции 1 мал (каталог; для компактирования — до `T` строк и их индексы), а при медленном диске WAL или зависшей синхронной реплике горячий путь стоит и без retention — его коммиты ждут то же самое.
- **Повторная проверка** ловит задачу, появившуюся между предпроверкой и `LOCK`: requeue (core §5.9) или enqueue с id из прошлых суток (отстающие часы клиента) — оба вставляют строку `queue` в том же statement, что и строку `jobs`. Проверка присоединённости по `oid` надёжна: чужой `DETACH` и компактирование тоже требуют `ACCESS EXCLUSIVE` на родителе, а компактирование меняет `oid` партиции — поэтому под, чей список устарел, не сжимает только что сжатую партицию повторно.
- **Живые строки копируются по массиву `@ids`,** прочитанному под блокировкой, а не подзапросом по `queue`: `id = ANY(@ids)` даёт индексный доступ по PK старой таблицы (индексы при `DETACH` и `RENAME` сохраняются) при любой статистике, тогда как для полусоединения планировщик мог бы выбрать seq scan партиции в десятки ГБ под блокировкой родителя.
- **`SELECT *` вместо списка колонок.** Партиции `jobs` создаёт только PgBolt через `LIKE` родителя (§5.2, §11); `ADD COLUMN` и `DROP COLUMN` на родителе распространяются на все партиции (добавленная колонка — в конец, удалённая становится `attisdropped` и в родителе, и в партиции). Поэтому логический порядок колонок (без удалённых) у старой партиции, новой таблицы (`LIKE` родителя в той же транзакции) и родителя совпадает: удалённых слотов у новой таблицы нет, у старой они есть, но `SELECT *` их не возвращает. Колонки, добавленные более новой схемой (rolling deploy, §4), переносятся автоматически; под блокировкой родителя схема `jobs` не меняется (`ALTER TABLE jobs` ждёт её). Генерируемых колонок в `jobs` нет (в них `INSERT … SELECT *` не вставил бы). Контракт проверяется тестом (§12).
- `CHECK` по диапазону не создаётся: `ATTACH` проверяет границы сканированием новой таблицы — не больше `T` строк, только что вставленных; `ADD CONSTRAINT`/`DROP CONSTRAINT` были бы двумя лишними DDL под блокировкой. Имена индексов новой партиции выбирает PostgreSQL (имена индексов остатка заняты — с числовым суффиксом); на имена индексов ничего не завязано.

**6. Транзакция 2** — на каждую отсоединённую таблицу (`jobs_YYYYMMDD` после отсоединения, `jobs_YYYYMMDD_r<oid>` после компактирования, остатки §5.2), родитель не блокируется; транзакция — так же через `BeginTransactionAsync`/`CommitAsync`:
```sql
SET LOCAL lock_timeout = '<RetentionLockTimeout>ms';
SELECT to_regclass(@table) = @oid::oid
   AND NOT EXISTS (SELECT 1 FROM pg_inherits WHERE inhrelid = @oid::oid) AS droppable;
-- droppable IS NOT TRUE → RollbackAsync, пропуск (таблица удалена, заменена или присоединена)
DROP TABLE {schema}.<table>;
```
`@oid` — из списка §5.2 (у остатка компактирования — `oid` бывшей партиции, он же суффикс имени). Проверка исключает удаление по имени присоединённой партиции: например, под с устаревшим списком нашёл `jobs_D` неприсоединённой по старому `oid`, а под тем же именем уже присоединена новая партиция компактирования. Между проверкой и `DROP` таблица присоединиться не может: прошлые сутки присоединяет только компактирование, и только новую таблицу, созданную в той же транзакции. `42P01` после ожидания блокировки (таблицу удалил другой под) — пропуск, в результат не попадает. Признак — SQLSTATE ошибки, он не зависит от `NOTICE`, `lc_messages`, `client_min_messages` и event trigger'ов.

**Корректность компактирования.**
- Под `ACCESS EXCLUSIVE` на родителе горячий путь не может менять строки `jobs`: все его statement'ы обращаются к `jobs` через родителя и блокируют его до выполнения. Набор строк `queue` в диапазоне тоже заморожен: строки `queue` вставляются и удаляются только statement'ами, которые затрагивают и `jobs` (enqueue, ack, fail, sweeper, cancel, requeue, release — worker §7.1: ветка отмены удаляет строку `queue` и финализирует `jobs` в одном statement, и statement ссылается на `jobs` в обеих ветках). Statement'ы, не касающиеся `jobs`, — heartbeat, promoter, первый statement cancel, trigger — продолжают работать: они меняют только поля строк `queue`, которые компактирование не читает.
- Задачи, уже взятые в lease, продолжают выполняться. Их ack/fail/heartbeat адресуют строку по id через родителя; после `COMMIT` pruning находит её в новой партиции тех же суток с теми же значениями. `DETACH`/`ATTACH` инвалидируют кэшированные планы, ссылающиеся на родителя.
- Терминальные строки закреплённой партиции удаляются вместе со старой таблицей — это согласуется с отсчётом retention от суток создания: срок истёк для всех строк партиции. Строки `queue` не трогаются.
- Взаимоблокировок с горячим путём нет: порядок наших блокировок — родитель `jobs`, затем партиции (как у запросов через родителя); на `queue` берётся `ACCESS SHARE`, совместимая с `ROW EXCLUSIVE` горячего пути; строки `queue` читаются по снимку, без блокировок строк.
- **Контракт HOT сохраняется:** новая партиция создаётся с `fillfactor = JobsFillFactor` (текущее значение настройки), собственных индексов не имеет — только индексы родителя, построенные при `ATTACH`.

**MVCC.** Компактирование, как `TRUNCATE`, не MVCC-безопасно. Перенесённые строки получают `xmin` транзакции 1, а старая таблица отсоединена; транзакция REPEATABLE READ или SERIALIZABLE, взявшая снимок до `COMMIT` транзакции 1 и впервые обратившаяся к `jobs` после него (обратись она раньше, её `ACCESS SHARE` на родителе не дала бы взять `LOCK`), видит новую партицию по каталогу, но не видит её строк: живые задачи сжатой партиции для неё пропадают. Горячий путь не затронут: все его statement'ы — READ COMMITTED, а в READ COMMITTED снимок statement'а берётся после получения блокировок. То же на **hot standby**: запрос REPEATABLE READ на реплике со снимком до воспроизведения компактирования не увидит живые строки; кроме того, воспроизведение `ACCESS EXCLUSIVE` на `jobs` конфликтует с запросами к `jobs` на реплике — они задерживают воспроизведение до `max_standby_streaming_delay` или отменяются (как и для обычного `DETACH`/`DROP`). `pg_dump` не затронут: он держит `ACCESS SHARE` на `jobs` всё время выгрузки, и retention получает `LockTimeout`. Фиксируется в XML-doc `RetentionCompactionMaxLiveJobs` (выход — порог `0`), в контракте части 6 (§11) и в §10.

**Обработка ошибок.**
- **Транзакция 1.** `55P03` (`lock_not_available`) на `LOCK` родителя или `DETACH` партиции → откат, все партиции группы — `Deferred(LockTimeout)`. `57014` (`query_canceled`) по `statement_timeout` при неотменённом токене или разрыв соединения до завершения `CommitAsync` (`idle_in_transaction_session_timeout`) → транзакция откатилась, все партиции группы — `Deferred(HoldTimeout)`, без исключения. Признак разрыва по idle-timeout: `PostgresException` с `SqlState = 25P03` **или** любое `NpgsqlException` при `conn.FullState`, содержащем `Broken` или `Closed` (через PgBouncer вместо `25P03` приходит обрыв без SQLSTATE или ошибка самого PgBouncer, например `08P01`); откат — по правилу п. 5 (только при открытом соединении, ошибки отката глотаются). Разрыв во время `CommitAsync` оставляет исход неизвестным — безвредно: следующий запуск строит список заново (§5.2). В обоих случаях — остановка по п. 2. Отмена токеном (Npgsql отправляет cancel, сервер отвечает `57014`, либо отмена между round-trip'ами) → откат (п. 5) и `OperationCanceledException`. **Любая другая ошибка** (включая `42P01`, `42P07`) → откат и исключение из `ApplyRetentionAsync`.
- **Предпроверки** (п. 1, п. 3, прогрев п. 4, запрос публикаций) — вне блокировки родителя: `55P03` → `Deferred(LockTimeout)` для этой партиции, обработка продолжается; `42P01` (`undefined_table`) в statement'е, обращающемся к партиции напрямую (`count` п. 1, прогрев), → она уже удалена другим подом, пропуск, в результат не попадает; `42P01` запроса к `queue` к партиции не относится — исключение. Сверка `oid` в п. 1 (до запросов или повторная после `count`) не `true` → пропуск, в результат не попадает. Прочие ошибки — исключение.
- **Транзакция 2.** `55P03` → откат, `Deferred(DropLockTimeout)`, обработка продолжается (родитель не затронут); таблица удаляется следующим запуском как остаток (§5.2). `droppable` не `true` → пропуск, в результат не попадает. `42P01` на `DROP` (таблицу удалил другой под, пока `DROP` ждал блокировку) → откат, пропуск, в результат не попадает. Отмена токеном → откат и `OperationCanceledException`. Любая другая ошибка по конкретной таблице → откат, лог Error (§8), `Deferred(DropFailed)`, обработка продолжается: таблица уже отсоединена, горячий путь её не видит, следующий запуск повторит удаление как остатка.
- После отсоединения (без компактирования) enqueue с id из удалённых суток падает с ошибкой «no partition of relation "jobs" found for row» — поведение core, не меняется. После компактирования такой enqueue проходит в новую партицию.

**Порог `RetentionCompactionMaxLiveJobs`.** Блокировка родителя при компактировании держится пропорционально числу `N` переносимых строк: чтение `N` id из PK `queue`, `N` выборок по PK старой таблицы с детоастом (прогреты, п. 4), вставка `N` строк, проверка границ и построение индексов родителя на `N` строках при `ATTACH`; изменения каталога и три RTT — константа. При `N = 1000` (строки `jobs` с `args` до нескольких КБ) это единицы-десятки мс — сопоставимо с `RetentionLockTimeout`. Верхняя граница валидации `10 000` — перенос с запасом укладывается в `HoldStatementTimeout` (2 с) на statement; при большем числе `INSERT` или `ATTACH` систематически упирался бы в таймаут (`Deferred(HoldTimeout)` каждым запуском). `0` выключает компактирование: закреплённые партиции ждут ухода живых задач, как партиции с живыми больше порога.

**Закреплённые партиции.** Закрепляют партицию, например: `Delay`/`RunAt` дальше `Rd` суток, очередь без потребителя (задачи копятся в Enqueued), задача с долгими ретраями. Сжатая партиция сжимается повторно, когда терминальных строк в ней наберётся не меньше `max(живых, 100)` (п. 1); после ухода последней живой задачи она отсоединяется и удаляется. Партиция с живыми больше порога (или при `Replicated`) занимает диск целиком; при `OverdueDays ≥ 7` — Warning (§8): такие задачи нужно выполнить, отменить или удалить вручную, либо временно поднять порог.

**Число партиций.** Закреплённая партиция (сжатая или нет) остаётся присоединённой до ухода последней живой задачи, поэтому число присоединённых партиций `jobs` сверху не ограничено: например, задачи с `RunAt` через год закрепляют по партиции на каждые сутки, в которые их ставили. Запросы без plan-time pruning (join dequeue) планируют и блокируют все партиции и их индексы: время планирования и число блокировок растут с числом партиций, блокировки сверх fast-path уходят в общую таблицу блокировок (её размер — `max_locks_per_transaction × (max_connections + max_prepared_transactions)`, при исчерпании — `out of shared memory`). Штатное число — `PartitionDaysAhead + Rd + 1` (будущие, непросроченные прошлые и сегодняшняя); `RetentionResult.AttachedJobsPartitions` — число после запуска, Warning (§8) при превышении `PartitionDaysAhead + Rd + 1 + 30` (30 — запас на закреплённые сутки). При `JobsRetention = null` Warning не выводится (рост на одну партицию в сутки — выбор пользователя, XML-doc). Влияние на dequeue проверяется бенчмарком части 7. Возможное развитие (не в этой части): объединять соседние закреплённые сутки в одну многодневную партицию при компактировании.

Следствие отсчёта от создания: задача, созданная в сутки `D` и завершившаяся в сутки `D + k`, хранится после завершения `Rd − k + 1` суток, а при `k > Rd` — до ближайшего запуска retention, который её удалит (для закреплённой партиции — до сжатия или отсоединения). Фиксируется в XML-doc `JobsRetention`.

### 5.4 Retention `job_events`

Кандидаты по `EventsRetention` (§5.2), без проверки задач и без компактирования. Группы до `K` партиций, та же предпроверка `pg_locks` (с родителем `job_events`) перед каждой группой, транзакция 1 на группу — как в §5.3 п. 5 (`BeginTransactionAsync`, пакеты А и Б, `CommitAsync`, те же таймауты удержания), транзакция 2 на каждую отсоединённую таблицу (§5.3 п. 6):

```sql
-- пакет А
SET LOCAL lock_timeout = '<RetentionLockTimeout>ms';
LOCK TABLE ONLY {schema}.job_events IN ACCESS EXCLUSIVE MODE;
SET LOCAL statement_timeout = '<HoldStatementTimeout + RetentionLockTimeout>ms';
SET LOCAL idle_in_transaction_session_timeout = '<HoldIdleTimeout>ms';
SELECT p.oid::bigint AS oid,
       to_regclass(p.rel) = p.oid
         AND EXISTS (SELECT 1 FROM pg_inherits i
                     WHERE i.inhrelid = p.oid AND i.inhparent = '{schema}.job_events'::regclass) AS attached
FROM unnest(@oids::bigint[]::oid[], @rels::text[]) AS p(oid, rel);      -- false → пропуск, таблица — в транзакцию 2
-- пакет Б: для каждой присоединённой партиции группы
ALTER TABLE {schema}.job_events DETACH PARTITION {schema}.job_events_YYYYMMDD;
```

Обработка ошибок и остановка (`LockTimeout`/`HoldTimeout` — вся группа отложена, остальные присоединённые кандидаты `job_events` в этом запуске не обрабатываются; `DropLockTimeout` и `DropFailed` — продолжение; прочие ошибки — исключение) — как в §5.3. События пишутся с `at = now()`, поэтому в прошлые партиции никто не пишет. Если `EventsRetention > JobsRetention`, события удалённых задач остаются без задач — безвредно (`GetJob` по несуществующей задаче события не читает).

### 5.5 Порядок

`ApplyRetentionAsync`:
1. `today` и список таблиц (§5.2) — один раз в начале.
2. Остатки `jobs` и `job_events` — транзакция 2 на каждый, при любом значении retention; `DropLockTimeout`/`DropFailed` по одной таблице обработку не прерывают (§5.3, «Обработка ошибок»).
3. `jobs` (§5.3): предпроверка всех присоединённых кандидатов (со сверкой `oid` по имени до и после обращения к партиции) и запрос публикаций, затем группы отсоединения, затем компактирования по одной.
4. `job_events` (§5.4).

`JobsRetention = null` / `EventsRetention = null` пропускает кандидатов соответствующей таблицы (остатки удаляются всё равно); оба `null` — только п. 1–2. Длительность запуска ограничена числом кандидатов: по транзакции 1 на группу и по транзакции 2 на таблицу; продление строки `maintenance_tasks` не нужно (перекрытие безвредно, §6.2).

### 5.6 Уборка `servers`

```sql
DELETE FROM {schema}.servers WHERE heartbeat_at < now() - @older_than;
```

Возвращает число удалённых строк. Удаляет только строки с устаревшим `heartbeat_at` (требование worker §7.2). `olderThan > 0` проверяется аргументом. Строка живого сервера, удалённая после его паузы дольше `olderThan`, восстанавливается его следующим heartbeat (§9.2).

### 5.7 Захват периодических задач (`PgBoltStore`, внутренний API для `PgBolt.Server`)

```sql
-- TryClaimMaintenanceAsync(name, interval) → DateTime? (UTC; claimed_at; null — не захвачено)
INSERT INTO {schema}.maintenance_tasks AS t (name, next_run_at, last_run_at)
VALUES (@name, now() + @interval, now())
ON CONFLICT (name) DO UPDATE
    SET next_run_at = EXCLUDED.next_run_at, last_run_at = EXCLUDED.last_run_at
    WHERE t.next_run_at <= now()
RETURNING t.last_run_at;

-- CompleteMaintenanceAsync(name, claimedAt, error, retryDelay): error = NULL при успехе; retryDelay = NULL — без ускоренного повтора
UPDATE {schema}.maintenance_tasks
SET last_error = @error,
    last_finished_at = now(),
    next_run_at = CASE WHEN @retry_delay IS NULL THEN next_run_at
                       ELSE LEAST(next_run_at, now() + @retry_delay) END
WHERE name = @name AND last_run_at = @claimed_at;
```

- Из двух конкурентных `TryClaim` строку получает ровно один: `ON CONFLICT DO UPDATE` блокирует существующую строку и проверяет `WHERE` по её последней версии, второй видит `next_run_at > now()` и не получает строки. Две конкурентные вставки отсутствующей строки: одна вставляет, вторая уходит в `ON CONFLICT` и видит свежий `next_run_at`.
- `last_run_at` — время начала последнего запуска и одновременно токен владения: `Complete` действует, только пока строку не захватил другой под. `Complete` запуска, который перекрылся новым (запуск или пауза пода дольше интервала), строку не меняет и не затирает результат нового.
- `last_finished_at` — время последнего `Complete`; `last_error` — текст исключения последнего завершённого запуска (`NULL` — успех или штатное отложение). Читаются частью 6: запуск идёт, если `last_finished_at < last_run_at` (или `NULL`) и `next_run_at > now()`.
- Под, упавший посреди задачи, не пишет `Complete`; задачу захватит любой под после `next_run_at`. Все операции идемпотентны, прерванная работа продолжается следующим запуском.

## 6. Расписание (`PgBolt.Server`)

### 6.1 Настройки `PgBoltProcessingOptions`

| Настройка | По умолчанию | Смысл |
|---|---|---|
| `MaintenancePollInterval` | 1 мин | Пауза цикла `housekeeping` (±20 %) |
| `PartitionsInterval` | 1 ч | Интервал задачи `partitions` в кластере |
| `ServersCleanupInterval` | 5 мин | Интервал задачи `servers` |
| `RetentionInterval` | 1 ч | Интервал задачи `retention` |
| `DeadServerTimeout` | 30 мин | Порог уборки `servers` |

Все — `> 0` и `≤ PgBoltServerOptions.MaxInterval` (1 сутки), как существующие `PromoterInterval`/`SweeperInterval`. Интервал записывается в `next_run_at` при захвате, поэтому при разных настройках на подах действует интервал пода, захватившего задачу последним (фиксируется в XML-doc).

XML-doc `RunMaintenance`: если ни один процесс, работающий со схемой, не выполняет обслуживание (у всех `RunMaintenance = false` и нет ручного режима §7), партиции кончатся через `PartitionDaysAhead` суток и enqueue начнёт падать; retention и уборка `servers` тоже не выполняются.

### 6.2 Цикл `housekeeping`

Третий цикл `ProcessingMaintenance` рядом с promoter и sweeper, запускается и останавливается вместе с ними (`RunMaintenance && серверов > 0`, worker §4.4 п. 6). Итерация — задачи по порядку `partitions`, `servers`, `retention`:

```
для каждой задачи:
    claimedAt = TryClaim(name, interval); null → следующая задача
    partitions: r = EnsurePartitionsAsync()                      // PgBoltOptions.PartitionDaysAhead
                r.TimedOut → лог (r.TodayPresent ? Warning : Error),
                             Complete(name, claimedAt, "lock_timeout", retryDelay = 1 мин)
                иначе      → Complete(name, claimedAt, null, null)
    servers:    RemoveDeadServersAsync(DeadServerTimeout)
                Complete(name, claimedAt, null, null)
    retention:  r = ApplyRetentionAsync()
                логи по r (§8); Deferred (включая LockTimeout и HoldTimeout) и Pinned
                ошибкой не считаются
                Complete(name, claimedAt, null, null)
    исключение операции → лог Error,
                Complete(name, claimedAt, e.Message, retryDelay = retention ? null : 1 мин)
```

- **Ускоренный повтор** (1 мин) — только для `partitions` (`TimedOut` и исключения) и `servers` (исключения). Для `partitions` он важен для горизонта и безвреден: `EnsurePartitionsAsync` ждёт до `PartitionLockTimeout` (2 с), а `ATTACH` берёт на родителе `SHARE UPDATE EXCLUSIVE`, не конфликтующий с горячим путём (core §4.4). Retention ускоренно не повторяется никогда, даже после исключения: каждый запуск может ставить горячий путь в очередь блокировкой родителя, поэтому не чаще раза в `RetentionInterval` (core §4.4 требует ограничивать повторы).
- Исключение `TryClaim`/`Complete` (недоступна БД) → лог Error, итерация прерывается, пауза до следующей. Цикл не останавливается ни при каких ошибках, кроме отмены.
- Остановка: общий токен `ProcessingMaintenance` отменяет текущую операцию; `Complete` не вызывается, строка остаётся захваченной до `next_run_at`. Прерванная транзакция откатывается целиком (`RollbackAsync(CancellationToken.None)` или dispose, §5.3 п. 5; компактирование атомарно); остаток между транзакциями 1 и 2 удалит следующий запуск. Отмена во время транзакции 1 — `OperationCanceledException`, а не `Deferred(HoldTimeout)`: `57014` считается таймаутом удержания только при неотменённом токене.
- Задачи выполняются последовательно одним циклом: retention задерживает `partitions`/`servers` только на этом поде; на других подах они захватываются как обычно.
- **Перекрытие** возможно, если запуск или пауза пода (GC, остановка контейнера, сеть) длится дольше `RetentionInterval`: другой под захватывает задачу, а `Complete` старого строку не меняет (§5.7). Оно безвредно без продления строки: каждое изменение партиций выполняется под блокировкой родителя с повторной проверкой присоединённости по `oid` и живых задач, имена остатков уникальны, `DROP` выполняется только для неприсоединённой таблицы с тем же `oid` (§5.3 п. 6), предпроверка п. 1 сверяет `oid` по имени до и после обращения к партиции, а `42P01` в предпроверках и в транзакции 2 обрабатывает уже удалённое. Худший случай — лишняя попытка `LOCK`: под с устаревшим списком не сожмёт повторно только что сжатую партицию (её `oid` сменился), а под со свежим списком — из-за порога терминальных строк.

### 6.3 Состав `IServerStore`

`IServerStore` (worker, внутренний) получает `TryClaimMaintenanceAsync`, `CompleteMaintenanceAsync`; меняется `HeartbeatAsync` (§9.2). Операции обслуживания вызываются через `IPgBoltMaintenance`, который `ProcessingMaintenance` получает из DI. Фейки в тестах подменяют оба.

### 6.4 Предупреждения при старте

Выводятся `PgBoltProcessingService` вместе с существующей проверкой `HostOptions.ShutdownTimeout`, только при `RunMaintenance`:
- `PgBoltOptions.PartitionDaysAhead × 1 сутки < 2 × PartitionsInterval` — одна неудачная итерация может оставить систему без партиции на следующие сутки;
- `DeadServerTimeout < 3 × max(HeartbeatInterval)` локальных серверов — строки живых серверов будут удаляться при коротких сбоях heartbeat и восстанавливаться следующим heartbeat (§9.2): сервер «мерцает» в dashboard.

## 7. Ручной режим (core-only)

Без `PgBolt.Server` пользователь вызывает `IPgBoltMaintenance` из своего планировщика: `EnsurePartitionsAsync()` — не реже раза в сутки (при `PartitionDaysAhead ≥ 2`), `ApplyRetentionAsync()` — раз в час, `RemoveDeadServersAsync` не нужен (серверов нет). `maintenance_tasks` в этом режиме не используется. Параллельные вызовы с разных подов безопасны, но дублируют работу и попытки `LOCK`; повторять `ApplyRetentionAsync` чаще раза в час после `LockTimeout`/`HoldTimeout` не следует. Рекомендации — в XML-doc интерфейса.

## 8. Ошибки и наблюдаемость

Логи пишет `ProcessingMaintenance` (категория `PgBolt.Processing`), кроме отмеченных:

| Ситуация | Уровень |
|---|---|
| Удалены партиции / остатки / строки `servers` | Information (с числами и сутками) |
| Закреплённые партиции `jobs` (`Pinned`, `Deferred` с `LiveJobs` и `Replicated`) | Information — одна сводная строка за запуск: число партиций, из них сжато в этом запуске, не сжато (терминальных мало), не сжимается (живых больше порога; публикация), суммарно живых задач, самые старые сутки |
| `Deferred` с `LiveJobs` и `OverdueDays ≥ 7` (константа `PinnedWarningDays`) | Warning на партицию: N живых задач (`T + 1` → «>T») больше `RetentionCompactionMaxLiveJobs`, партиция не сжимается и занимает диск целиком до их ухода |
| `Deferred` с `Replicated` и `OverdueDays ≥ 7` | Warning, одна строка за запуск: компактирование пропущено, потому что `jobs` или её партиции входят в публикацию логической репликации (§5.3 п. 1); число таких партиций и самые старые сутки |
| `AttachedJobsPartitions > PartitionDaysAhead + Rd + 1 + 30` (при `JobsRetention ≠ null`) | Warning, одна строка за запуск: число присоединённых партиций `jobs` и штатное число; закреплённые сутки замедляют dequeue (§5.3, «Число партиций») |
| `Deferred` с `HoldTimeout` | Warning, одна строка на таблицу за запуск, при любом `OverdueDays`: удержание блокировки родителя упёрлось в `statement_timeout`/`idle_in_transaction_session_timeout` — горячий путь стоял до границы удержания; причина — медленный диск или пауза процесса (GC) |
| `Deferred` с `LockTimeout`/`DropLockTimeout` | Одна строка на таблицу за запуск: число партиций и наибольший `OverdueDays`. Warning при наибольшем `OverdueDays ≥ 1` (удаление систематически блокируют долгие запросы к `jobs`/`job_events` или держатель самой партиции — autovacuum, прямой запрос), иначе Debug. Кандидаты, не обработанные после остановки, в строку не входят; самые просроченные среди отсоединяемых — в отложенной группе (§5.3 п. 2) |
| `Deferred` с `DropFailed` | Error на таблицу: имя таблицы, сутки и `Error`; `DROP` отсоединённой таблицы упал не по `lock_timeout`, повтор — следующим запуском как остатка (§5.3, «Обработка ошибок») |
| `EnsurePartitionsAsync` вернул `TimedOut`, `TodayPresent = true` | Warning (повтор через 1 мин) |
| `EnsurePartitionsAsync` вернул `TimedOut`, `TodayPresent = false` | Error: партиции на текущие сутки нет, enqueue падает (повтор через 1 мин) |
| Исключение операции, `TryClaim`, `Complete` | Error |
| Heartbeat: строки `servers` нет, сервер зарегистрирован заново (`LeaseKeeper`) | Warning |
| Ошибка повторной регистрации (`LeaseKeeper`) | Warning (повтор при следующем heartbeat) |
| Версия схемы новее кода (`PgBoltInitializer`) | Warning |

`LockTimeout` и `HoldTimeout` в `last_error` не записываются; `last_error` — только исключения и `TimedOut` задачи `partitions`. Метрики (удалённые, сжатые и отложенные партиции, `OverdueDays`, число живых задач в закреплённых, число присоединённых партиций, длительность удержания блокировки родителя, возраст `last_run_at`) — часть 7.

## 9. Изменения core и worker

Реализуются вместе с частью 2; тексты core §4.4, §4.7, §5.5 и worker §6.2, §7.2, §8.1 при реализации приводятся в соответствие.

### 9.1 Протокол удаления партиции (core §4.4)

Протокол core §4.4 заменяется протоколом §5.3–§5.4 (обоснование — §2): `LOCK TABLE ONLY` на родителе и сразу после него таймауты удержания; группа до `K` партиций под одной блокировкой, проверки (присоединённость по `oid`, Pending/Awaiting) одним запросом, `DETACH PARTITION` одним пакетом; `DROP TABLE` — отдельной транзакцией на таблицу, только если таблица с тем же `oid` не присоединена; остатки удаляются следующими запусками. Фраза core §4.4 «иначе из неё удаляются терминальные строки старше retention» заменяется компактированием (§5.3). Порядок блокировок (родитель → партиция) совпадает с порядком запросов через родителя. «Часть 2 ограничивает число повторов»: не больше одной неудачной попытки на таблицу за запуск, запуски — не чаще `RetentionInterval` (§6.2); алерт — Warning (§8), метрика — часть 7. В core фиксируется запрет внешних ключей на `jobs` (§11).

### 9.2 Самовосстановление строки `servers` (core §5.5, worker §6.2, §7.2)

Сейчас heartbeat только обновляет `servers` (0 строк, если строку удалили), и живой сервер после паузы дольше `DeadServerTimeout` исчезает из `servers` до рестарта. Изменения:

**Регистрация — upsert** (worker §7.2):
```sql
INSERT INTO {schema}.servers (id, name, host, queues, capacity, started_at, heartbeat_at)
VALUES (@id, @name, @host, @queues, @capacity, now(), now())
ON CONFLICT (id) DO UPDATE
    SET name = EXCLUDED.name, host = EXCLUDED.host, queues = EXCLUDED.queues,
        capacity = EXCLUDED.capacity, heartbeat_at = now();          -- started_at не меняется
```
Строка, удалённая уборкой, при восстановлении получает `started_at` = момент восстановления (прежнее значение утеряно вместе со строкой).

**Heartbeat сообщает, обновлена ли строка `servers`** (core §5.5, worker §8.1):
```sql
WITH s AS (
    UPDATE {schema}.servers SET heartbeat_at = now() WHERE id = @server
    RETURNING 1
),
l AS MATERIALIZED (
    SELECT job_id FROM {schema}.queue
    WHERE job_id = ANY(@ids) AND lease_id = ANY(@lease_ids) AND lease_owner = @server
    ORDER BY job_id                                -- порядок захвата core §5.3 не меняется
    FOR UPDATE
),
u AS (
    UPDATE {schema}.queue q SET lease_until = now() + @lease
    FROM l WHERE q.job_id = l.job_id
    RETURNING q.job_id, q.lease_id, q.cancel_requested
)
SELECT EXISTS (SELECT 1 FROM s) AS server_present, u.job_id, u.lease_id, u.cancel_requested
FROM (VALUES (1)) AS one(x) LEFT JOIN u ON true;
```
- Результат всегда содержит хотя бы одну строку: при пустом `u` — одну строку с `job_id IS NULL`. `server_present` одинаков во всех строках (некоррелированный подзапрос, вычисляется один раз). Семантика продления lease не меняется.
- Сигнатура: `Task<HeartbeatResult> HeartbeatAsync(Guid serverId, IReadOnlyCollection<LeaseRef> leases, TimeSpan lease, CancellationToken ct)` вместо `Task<IReadOnlyList<HeartbeatLease>>`; `public sealed record HeartbeatResult(bool ServerPresent, IReadOnlyList<HeartbeatLease> Leases)` (`PgBoltStore`, `IServerStore`, `PgBoltServerStore`). `Leases` — строки с `job_id IS NOT NULL`.
- `LeaseKeeper` получает `ServerRegistration` своего сервера (конструктор; передаёт `PgBoltServer`). Повторная регистрация выполняется внутри `HeartbeatCoreAsync`, после обработки успешного ответа (шаги 3–5 worker §6.2): при `ServerPresent = false` — `RegisterServerAsync(registration)` с токеном, связанным из токена остановки цикла и таймаута `HeartbeatInterval / 2`, и лог Warning; ошибка — лог Warning, повтор при следующем heartbeat (он снова вернёт `false`).
- **Расписание.** Вызов с `sentAt = S` завершается не позже `S + 0.5 HI`, регистрация — не позже `S + HI`. Плановый следующий `sentAt = S + HI × (1 ± 0.1)`, т. е. в `[S + 0.9 HI, S + 1.1 HI]`; цикл ждёт завершения `HeartbeatCoreAsync`, поэтому плановый момент, наступивший во время регистрации, сдвигается к её концу (не позже `S + HI`; `MonoClock.Until` сводит отрицательную задержку к нулю). Итого следующий `sentAt ≤ S + 1.1 HI`, и граница «следующий успешный ответ не позже `S + 1.6 HI`» (worker §6.2) сохраняется; дальнейшее расписание отсчитывается от фактического `sentAt`, и та же оценка действует для каждого шага.
- **Воскрешения строки после остановки нет:** `LeaseKeeper.StopAsync` отменяет токен цикла и дожидается цикла вместе с идущей регистрацией (worker §6.4 п. 5) до удаления строк серверов (п. 6).

### 9.3 Прочее

- `IPgBoltMaintenance.EnsurePartitionsAsync(int? daysAhead = null)` — `null` = `PgBoltOptions.PartitionDaysAhead` (§5.1).
- `PgBoltInitializer`: при `AutoMigrate = false` ошибка только при `version < LatestVersion` (или отсутствии схемы); `version > LatestVersion` — Warning при любом `AutoMigrate`. `PgBoltMaintenance.EnsurePartitionsAsync` вызывает `MigrateAsync` только при `AutoMigrate && (version is null || version < LatestVersion)` (§4).
- `IPgBoltMaintenance` получает `ApplyRetentionAsync`, `RemoveDeadServersAsync`; `PgBoltOptions` — настройки §5.1.

## 10. Обновление

- **Первый запуск retention удаляет всё старше срока.** До части 2 ничего не удалялось; после обновления первый запуск удалит все партиции `jobs` и `job_events` старше `JobsRetention`/`EventsRetention` (по умолчанию 7 суток) и сожмёт закреплённые (не больше порога живых задач, при достаточном числе терминальных). Сотни отсоединяемых партиций обрабатываются группами по `K`: остановок горячего пути в `K` раз меньше, чем партиций; компактируемые — по одной, каждая — короткая остановка. Чтобы сохранить историю, задайте `JobsRetention`/`EventsRetention` (или `null`, только кодом) до обновления. Фиксируется в XML-doc и changelog.
- **Порядок раскатки.** Сначала миграция V002 (первый под нового релиза с `AutoMigrate = true` или скрипт `GetScript(schema, fromVersion: 1)`), затем поды. Поды предыдущего релиза продолжают работать на V002: миграция только добавляет таблицу; компактирование сохраняет строки взятых ими задач (§5.3). Ограничение предыдущего релиза: его `PgBoltInitializer` сравнивает версию через `!=`, поэтому под старого релиза с `AutoMigrate = false`, **перезапущенный** после применения V002, не стартует — раскатку нужно завершать без пауз. Старый под с `AutoMigrate = true` стартует (нечего применять). Начиная с этого релиза версия схемы новее кода — Warning (§4), и следующие аддитивные миграции раскатываются без этого ограничения.
- Формат строк `servers` не меняется; heartbeat и upsert регистрации (§9.2) совместимы со строками старых подов. Старые поды своих строк не восстанавливают.
- **Breaking changes API до 1.0.** `IPgBoltMaintenance` получает новые методы (`ApplyRetentionAsync`, `RemoveDeadServersAsync`), а `EnsurePartitionsAsync` — сигнатуру `(int? daysAhead = null, …)`: пользовательские реализации и фейки интерфейса (в том числе моки в тестах приложений) перестают компилироваться и должны реализовать новые члены и новую сигнатуру. Вызовы `EnsurePartitionsAsync` с явным `int` совместимы по исходному коду, не бинарно. Внутренние: `IServerStore`, `HeartbeatAsync`. Фиксируется в changelog.
- **Риски, которые нужно знать при обновлении** (XML-doc и changelog):
  - *Снимки REPEATABLE READ/SERIALIZABLE* (primary и hot standby), взятые до компактирования, не видят живые задачи сжатой партиции (§5.3, «MVCC»); READ COMMITTED (горячий путь, dashboard) не затронут. Выход — `RetentionCompactionMaxLiveJobs = 0`.
  - *Hot standby.* Воспроизведение `ACCESS EXCLUSIVE` на `jobs`/`job_events` конфликтует с запросами к ним на реплике: ждёт до `max_standby_streaming_delay`, затем запросы отменяются; при `synchronous_commit = remote_apply` это задерживает и коммиты primary.
  - *Синхронная репликация.* `COMMIT` транзакции retention таймаутами удержания не ограничен (§5.3 п. 5): при зависшей синхронной реплике он держит блокировку родителя до её ответа — но горячий путь в этом случае стоит и без retention.
  - *Логическая репликация и CDC.* При публикации `jobs` или её партиций компактирование не выполняется (`Deferred(Replicated)`): закреплённые партиции занимают диск целиком. Отсоединение и `DROP` подписчику не передаются — удаление на подписчике остаётся задачей его владельца.
  - *Число партиций.* Закреплённые сутки остаются присоединёнными до ухода живых задач, при `JobsRetention = null` партиции копятся без ограничения; с их числом растут время планирования и число блокировок dequeue (§5.3, «Число партиций»; Warning §8).

## 11. Контракты для других частей

- **Все части:** внешние ключи, ссылающиеся на `jobs` (и `job_events`), запрещены — `DETACH` партиции проверяет ссылки сканированием ссылающейся таблицы под блокировкой родителя и при найденной ссылке падает с `23503`. Партиции создаёт только PgBolt (`LIKE` родителя), колонки меняются только `ALTER TABLE` родителя, генерируемых колонок в `jobs` нет (§5.3, `SELECT *`).
- **Часть 5 (Workflows):** живые задачи = Pending ∪ Awaiting. Предпроверка, повторная проверка под блокировкой (`has_live`, `ids`), подсчёт `LiveJobs` и массив `@ids` компактирования и прогрева (§5.3) дополняются Awaiting-задачами диапазона по индексу (core §4.4); строки зависимостей Awaiting-задач не трогаются (id не меняется) и ссылаются на `jobs` без внешнего ключа. Statement'ы части 5, создающие Awaiting-задачи или меняющие их состояние, должны обращаться к `jobs` через родителя (тогда набор живых под блокировкой заморожен, как в §5.3). Порог «терминальных не меньше `max(живых, 100)`» остаётся верным: терминальные = строки партиции − живые.
- **Часть 6 (Dashboard):** читает `maintenance_tasks` (`last_run_at`, `last_finished_at`, `last_error`, `next_run_at`); ручной запуск задачи — upsert `INSERT INTO {schema}.maintenance_tasks (name, next_run_at) VALUES (@name, now()) ON CONFLICT (name) DO UPDATE SET next_run_at = now()`, потому что строка создаётся первым захватом и может ещё не существовать (во время идущего запуска даёт перекрытие, безвредное, §6.2). **`jobs` dashboard читает только в READ COMMITTED** (снимок на statement): снимок REPEATABLE READ, взятый до компактирования, не видит живые задачи сжатой партиции (§5.3, «MVCC»). Экран, которому нужна согласованность нескольких выборок, собирает данные одним statement'ом, а не транзакцией REPEATABLE READ. Opt-in индексы по `args` проектируются в части 6 в рамках контракта HOT; компактирование строит их на новой партиции при `ATTACH`.
- **Часть 7:** метрики §8 (включая длительность удержания блокировки родителя, число `HoldTimeout` и число присоединённых партиций), бенчмарк влияния числа присоединённых партиций `jobs` на dequeue (планирование, блокировки, `max_locks_per_transaction`), настройка autovacuum `queue`, мониторинг bloat, `COPY` против `unnest`.
- **Будущие периодические задачи** (например, часть 4) используют `maintenance_tasks` через `TryClaim`/`Complete`; строка создаётся первым захватом, миграция для неё не нужна.

## 12. Тестирование

Интеграционные тесты — реальный PostgreSQL через `PostgresFixture`/`TestDb` (соединения через PgBouncer в transaction mode, как в фикстуре). Время не подменяется: `today` берётся из БД, тесты создают **прошлые** партиции хелпером с тем же DDL, что `PartitionManager` (`CREATE TABLE … (LIKE …)` + `ATTACH`), и строки с UUIDv7 из тех же суток. `K`, `HoldStatementTimeout`, `HoldIdleTimeout` — поля `RetentionTuning` (§5.3): тест создаёт свой экземпляр и передаёт его в `PgBoltMaintenance` через internal-конструктор, глобальное состояние не меняется (тесты независимы и параллелятся); тестовые хуки — после предпроверки п. 1, после предпроверки `pg_locks`, после прогрева (перед `LOCK`), между пакетами А и Б, между пакетом Б и `COMMIT`, после `COMMIT` транзакции 1; хуки фиксируют порядок шагов.

**Retention (`PgBolt.Postgres.Tests`):**
- Граница кандидата: при `Rd` партиция `today − 1 − Rd` удаляется, `today − Rd` остаётся; сегодняшняя и будущие не удаляются. Округление `Retention` вверх до суток.
- `JobsRetention = null` / `EventsRetention = null` отключают кандидатов соответствующей таблицы; разные сроки применяются независимо; оба `null` — только список таблиц и удаление остатков.
- Валидация: `≤ 0`, `> 3650 суток`, `RetentionLockTimeout > 1 мин`, `RetentionCompactionMaxLiveJobs < 0` и `> 10 000` отклоняются; `null` и порог `0` принимаются.
- Компактирование: партиция с Pending-строками (в т. ч. взятыми в lease) и терминальными строками → живые строки перенесены с теми же значениями всех колонок, терминальные удалены, имя партиции прежнее, oid новый, `fillfactor` = `JobsFillFactor`, есть PK родителя, `CHECK`-ограничений сверх родительских нет, остатка `jobs_D_r<oid>` нет; `queue` не изменилась. После ack задачи следующий запуск удаляет партицию целиком.
- Контракт `SELECT *`: у всех партиций `jobs` список колонок (`attname` по `attnum`, без `attisdropped`) совпадает с родителем — для партиций, созданных до и после `ALTER TABLE jobs ADD COLUMN extra text` и до и после `DROP COLUMN`; генерируемых колонок в `jobs` нет. Компактирование после `ADD COLUMN` (значение заполнено у живых строк) переносит его; после `ADD` и `DROP COLUMN` (в старой партиции — удалённый слот, в новой его нет) переносит все значения.
- Взятая задача после компактирования: ack, fail с retry, окончательный fail, release (worker §7.1, обе ветки) и heartbeat по её lease работают, строка `jobs` получает итог в новой партиции.
- Порог живых: живых `= T` → компактирование; `T + 1` → `Deferred(LiveJobs)` с `LiveJobs = T + 1`, партиция не изменена; `T = 0` → `Deferred(LiveJobs)` при любом числе живых.
- Порог терминальных: 50 живых и 99 терминальных → `Pinned(Compacted = false)`, `LOCK` не выполняется (хук); 50 и 100 → сжата; 300 живых и 299 терминальных → `Pinned(Compacted = false)`; 300 и 300 → сжата. Партиция только из живых строк → `Pinned(Compacted = false)`. Сжатая партиция: следующий запуск без новых терминальных строк её не трогает.
- Прогрев: для каждой компактируемой партиции порядок — предпроверка `pg_locks` → прогрев → `LOCK` (хуки), прогрев выполняется отдельно перед каждой транзакцией 1. `EXPLAIN` запроса прогрева на партиции с `args` больше 2 КБ показывает чтение heap по PK партиции — Index Scan или Bitmap Heap Scan, но не Index Only Scan.
- Транзакция 1: `NOT attached`, `ids` больше `T`, пустая группа отсоединения → `RollbackAsync` без пакета Б (хук между пакетом Б и `COMMIT` не вызывается). Retention на `NpgsqlDataSource` с `Multiplexing = true` проходит без исключений.
- Таймауты удержания (в партиции живые задачи и не меньше 100 терминальных строк — иначе порог `max(L, 100)` даст `Pinned(Compacted = false)` без транзакции 1): хук между пакетами А и Б (и отдельно — между пакетом Б и `COMMIT`) спит дольше `HoldIdleTimeout` → сервер закрывает соединение, транзакция откатилась, партиция не изменена, `Deferred(HoldTimeout)`, остальные присоединённые кандидаты `jobs` не тронуты и в результат не попали, `job_events` обработан, исключения нет; следующий запуск (без паузы) сжимает партицию; горячий путь и пул соединений после разрыва работают. Уменьшенный `HoldStatementTimeout` и тестовый `pg_sleep` в пакете Б → `57014`, откат, `Deferred(HoldTimeout)`.
- Область `SET LOCAL` — на прямом соединении (без PgBouncer, пул на одно соединение): после `CommitAsync` и после `RollbackAsync` транзакции 1 `SHOW lock_timeout`, `SHOW statement_timeout`, `SHOW idle_in_transaction_session_timeout` на том же соединении возвращают значения по умолчанию.
- Отмена: токен отменён в хуке между пакетами А и Б → `OperationCanceledException`, не `HoldTimeout`; транзакция откачена (партиция не изменена, enqueue в другом соединении проходит сразу), соединение из пула пригодно.
- Прочие ошибки транзакции 1: хук создаёт таблицу `jobs_D_r<oid>` → `RENAME` в пакете Б падает (`42P07`), откат пакета, исключение из `ApplyRetentionAsync`, партиция не изменена.
- Публикация: `CREATE PUBLICATION … FOR TABLE {schema}.jobs` и отдельно `FOR ALL TABLES` → партиция, которую нужно сжать, — `Deferred(Replicated)` с числом живых, не изменена; партиции без живых задач отсоединены и удалены; `job_events` обработан. Без публикации тот же набор сжимается.
- Повторная проверка под блокировкой (в компактируемой партиции не меньше 100 терминальных строк — иначе порог `max(L, 100)` даст `Pinned(Compacted = false)`): requeue терминальной строки между предпроверкой и `LOCK` (хук) — в партиции группы отсоединения → она не отсоединена и не попала в результат, остальные партиции группы удалены, следующий запуск её сжимает; в компактируемой → requeue'нутая строка перенесена. `queue` и `jobs` согласованы, осиротевшей строки `queue` нет.
- Группы: 25 отсоединяемых кандидатов при `K = 10` → 3 транзакции 1; три компактируемые партиции → три транзакции 1, каждой предшествуют своя предпроверка `pg_locks` и свой прогрев; `DROP` — по транзакции на таблицу.
- Остатки: хук после `COMMIT` транзакции 1 прерывает операцию → остаются `jobs_D` (после отсоединения) и `jobs_D_r<oid>` (после компактирования), новая `jobs_D` присоединена; следующий запуск удаляет остатки — в том числе при `JobsRetention = null` и при сутках, ещё не ставших кандидатом, — и сообщает их. Другое соединение держит `ACCESS SHARE` на остатке → `DropLockTimeout`, остальное обработано, горячий путь не затронут. Остаток `jobs_D_r<oid>`, удалённый в том же запуске, что и компактирование, — партиция только в `Pinned(Compacted = true)`, `DroppedCompactionRemnants` его не учитывает; при `ACCESS SHARE` на нём (хук после `COMMIT` транзакции 1) — ещё и `Deferred(DropLockTimeout)` тех же суток.
- `DropFailed`: транзакция 2 одной таблицы падает с ошибкой, отличной от `55P03` (тестовый event trigger на `sql_drop` с `RAISE` для этой таблицы) → `Deferred(DropFailed)` для неё, остальные таблицы удалены, исключения нет; следующий запуск (без триггера) удаляет её как остаток. Отмена токеном в транзакции 2 → `OperationCanceledException`, не `DropFailed`.
- `DROP` по `oid`: запуск A получил список (хук после списка), другое соединение сжимает `jobs_D` (под тем же именем присоединена новая таблица) → A считает старый `oid` неприсоединённым, транзакция 2 не удаляет присоединённую `jobs_D` (имя указывает на другой `oid`), живые строки на месте; удаляется только `jobs_D_r<oid>` с исходным `oid`. Остаток, вместо которого хук создал присоединённую таблицу с тем же именем, не удаляется.
- `ONLY`: другое соединение держит `SHARE UPDATE EXCLUSIVE` на **сегодняшней** партиции `jobs` и `job_events` в открытой транзакции (как autovacuum) → старые партиции удалены без `LockTimeout`.
- Предпроверка `pg_locks`: `SHARE UPDATE EXCLUSIVE` на самой **старой** партиции напрямую → `Deferred(LockTimeout)` без `LOCK` родителя (хук), остальные партиции группы обработаны. Транзакция, читавшая `jobs` через родителя без pruning (держит блокировки всех партиций), предпроверкой не учитывается → `LOCK` родителя получает `lock_timeout`. Держатель партиции, появившийся после предпроверки (хук), → `lock_timeout` в `DETACH`, откат (для компактирования — вместе с переносом), `Deferred(LockTimeout)` для всей группы.
- `lock_timeout` `jobs`: другое соединение держит `ACCESS SHARE` на `jobs`, кандидатов больше `K` → все партиции первой группы `Deferred(LockTimeout)`, остальные присоединённые кандидаты `jobs` не тронуты и в результат не попали, `job_events` обработан; enqueue/dequeue проходят; после освобождения следующий запуск удаляет.
- `lock_timeout` `job_events`: `ACCESS SHARE` на `job_events` → `Deferred(LockTimeout)` для группы `job_events`, остальные её кандидаты не тронуты, `jobs` обработан.
- `AttachedJobsPartitions`: равно числу присоединённых партиций `jobs` после запуска (с закреплёнными сутками и без; отдельный запрос к `pg_inherits` в конце операции, §5.1).
- Горячий путь под нагрузкой: параллельные enqueue/dequeue/ack/heartbeat/release во время компактирования — без ошибок, все задачи согласованы.
- MVCC (документирующий тест): транзакция REPEATABLE READ берёт снимок (запрос к `queue`) до компактирования и читает `jobs` после него → живые задачи сжатой партиции не видны; та же выборка в READ COMMITTED их видит.
- Имена: `jobs_2026101`, `jobs_20261002_old`, `jobs_20261399` (неверная дата), `jobs_YYYYMMDD`, присоединённая к чужому родителю, `jobs_YYYYMMDD_r1`, присоединённая к `jobs`, — не трогаются.
- Перекрытие: два `ApplyRetentionAsync` параллельно на одном наборе (с отсоединяемыми и компактируемыми партициями) — каждая партиция удалена ровно один раз, живые строки не потеряны и не задвоены, сжатая партиция не сжата повторно, исключений нет; партиция, удалённая другим соединением между списком и предпроверкой (хук), — сверка `oid` в предпроверке (`to_regclass` → `NULL`) обрабатывает её как «уже удалена»; удалённая, пока `count` предпроверки ждал блокировку, — `42P01` в `count` обрабатывается так же; заменённая (сжатая) другим соединением, пока `count` ждал блокировку, — повторная сверка `oid` после `count` обрабатывает её как «уже удалена», новая таблица не затрагивается.
- UTC: строка подключения с `Timezone=Pacific/Kiritimati` (+14) и `Timezone=Etc/GMT+12` (−12) — кандидаты и `today` совпадают с UTC-вариантом.
- `EnsurePartitionsAsync()` без аргумента использует `PgBoltOptions.PartitionDaysAhead`.

**`servers`, heartbeat и `maintenance_tasks`:**
- Удаляются только строки с `heartbeat_at < now() − olderThan`.
- `RegisterServerAsync` повторно для существующей строки — без ошибки, `started_at` не меняется, `heartbeat_at` обновлён.
- Heartbeat: `ServerPresent = true` при наличии строки (с пустым и непустым списком lease), `false` после её удаления; lease при удалённой строке продлеваются.
- `TryClaim` без строки создаёт её и захватывает; 10 параллельных `TryClaim` одной задачи (со строкой и без) — ровно один не `null`.
- `Complete` с устаревшим `claimedAt` строку не меняет; `Complete` пишет `last_finished_at`; с `retryDelay` сокращает `next_run_at` до `now() + retryDelay`, без — не меняет.

**Worker (`PgBolt.Server.Tests`):**
- Юнит-тесты цикла `housekeeping` на фейках: захвачено → выполнено → `Complete(null)`; не захвачено → не выполнено; исключение операции → `Complete(error)`, следующая задача выполняется, цикл жив; `partitions` `TimedOut` → `Complete("lock_timeout", 1 мин)`, лог Warning при `TodayPresent = true` и Error при `false`; retention с `Deferred` (включая `LockTimeout` и `HoldTimeout`)/`Pinned` → `Complete(null, null)`; исключение retention → `Complete(error, null)` без ускоренного повтора; отмена прерывает цикл без `Complete`; уровни логов §8: одна сводная строка Information о закреплённых партициях, Warning на партицию для `Deferred(LiveJobs)` при `OverdueDays ≥ 7`, одна строка Warning для `Deferred(Replicated)` при `OverdueDays ≥ 7`, одна строка на таблицу для `HoldTimeout` (Warning), Error на таблицу для `DropFailed` и для `LockTimeout` группы (Warning при наибольшем `OverdueDays ≥ 1`, иначе Debug), Warning при `AttachedJobsPartitions` выше порога и его отсутствие при `JobsRetention = null`.
- `LeaseKeeper`: `ServerPresent = false` → `RegisterServerAsync` и Warning; ошибка регистрации → Warning и повтор при следующем heartbeat; `ServerPresent = true` → регистрации нет; регистрация, закончившаяся после планового `sentAt`, сдвигает только следующий вызов (не позже конца регистрации), дальнейшее расписание — от фактического `sentAt`; `StopAsync` во время регистрации отменяет её и дожидается.
- Интеграционный: два хоста на одной схеме с просроченной партицией — retention выполнен одним из них, `last_run_at`/`last_finished_at` записаны.
- Интеграционный: строка `servers` живого сервера удалена → восстановлена следующим heartbeat; после остановки хоста строки нет.
- Предупреждения §6.4.

**Миграции:** `GetScript(schema, fromVersion: 1)` содержит V002; обновление V001 → V002 на схеме с данными проходит; `AutoMigrate = false` без V002 — старт падает с сообщением о версии.
