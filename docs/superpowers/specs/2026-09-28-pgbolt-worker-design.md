# PgBolt — часть 3: Worker runtime (Server)

Статус: одобрено ревью, реализовано (ред. 4; план `docs/superpowers/plans/2026-09-28-pgbolt-worker.md`) · Дата: 2026-09-28 · Карта проекта: `2026-09-26-pgbolt-roadmap.md` · Основа: `2026-09-26-pgbolt-core-design.md` (далее «core»)

## 1. Цель и рамки

Пакет `PgBolt.Server`: хост, который забирает задачи из `queue`, выполняет их через registry исполнителей в отдельном DI scope, подтверждает исходы и обслуживает lease, promoter и sweeper. Весь SQL горячего пути уже есть в core; часть 3 — runtime поверх него, два небольших statement'а (§7) и точечные изменения core (§8).

**Входит:** виртуальные серверы, слоты, fetch-цикл с адаптивным polling, выполнение с фильтрами и таймаутом, пакетный ack, fail/retry/NoExecutor, heartbeat с доставкой отмены и обнаружением потерянных lease, promoter и sweeper, graceful shutdown, политика retry по умолчанию.

**Не входит:**
- `LISTEN`/`NOTIFY` — исключены из проекта (§2).
- Кластерный лимит конкурентности на очередь и веса очередей — отдельная часть 3b; в этой части закладываются точки расширения (§4.2, §4.3).
- Периодический `EnsurePartitionsAsync`, retention, уборка `servers` — часть 2.
- OpenTelemetry-инструментирование — часть 7 (встраивается фильтром, §3.6). Пересмотрено в части 7a: инструментирование встроено в `JobRunner`, а не фильтром (`2026-10-16-pgbolt-observability-design.md`, §2).

### Критерии успеха
- 5–20k jobs/sec на одном узле PG, напрямую и через PgBouncer в transaction mode.
- Ни одна задача не теряется; результат выполнения с потерянным lease не подтверждается.
- Выполнение, продление lease которого не подтверждено, отменяется не позже чем за `HeartbeatInterval` до истечения его lease — независимо от того, когда оно было взято относительно последнего успешного heartbeat.
- Lease задачи, которую runtime перестал выполнять и чей исход перестал отправлять, истекает не позже чем через `LeaseDuration`, даже при живом поде; дальше задачу обрабатывает sweeper.
- Отмена выполняющейся задачи доходит не позже чем за `HeartbeatInterval`.
- Деплой (graceful shutdown) не расходует попытки задач, корректно останавливающихся по токену, при любом числе виртуальных серверов в процессе.
- Число соединений процесса ограничено пулом `NpgsqlDataSource`; постоянно удерживаемых соединений нет.

## 2. Принятые решения

| Вопрос | Решение | Причина |
|---|---|---|
| Wakeup между подами | Без `LISTEN`/`NOTIFY`. In-process сигнал (core §5.10) + адаптивный polling + сигнал от promoter'а. `IWakeupSignal` остаётся публичной точкой расширения (например, Redis pub/sub — не поставляется) | `LISTEN` держит постоянное прямое соединение в обход PgBouncer на каждый под (20 подов = 20 слотов `max_connections`, растёт с HPA); `NOTIFY` берёт глобальный lock на коммите и сериализует коммиты на 5–20k/s; под нагрузкой polling и так идёт без пауз |
| Пробуждение диспетчера | Собственное latched auto-reset событие диспетчера; `IWakeupSignal` получает подписку на очередь `Subscribe(queue, callback)` вместо `WaitAsync` (§4.3, §8.2) | `WaitAsync` не сообщает, какая очередь сработала, и теряет сигнал, пришедший без ожидающего; пробуждение по слоту через отмену токена даёт исключение на каждое освобождение слота |
| Heartbeat | Продление `lease_until` по строкам, но **только известных runtime lease** — выполняющихся или ждущих отправки исхода (core §5.5 с фильтром по `lease_id`, §8.1). Liveness по `servers` не делаем | Цена ≈ «взятые задачи ÷ интервал» UPDATE'ов/с (20 подов × 50 слотов / 15 с ≈ 70 строк/с против 20k/с dequeue-UPDATE'ов). Фильтр нужен, чтобы строка, брошенная runtime (исход не отправлен, dequeue закоммичен, но ответ не получен), не продлевалась бесконечно, пока жив под, а истекала и уходила sweeper'у. Пересмотр liveness — только по бенчмарку части 7, без изменения API воркера |
| Сбой БД во время выполнения | У каждого выполнения — локальная нижняя граница его lease `validUntil` (от начала его dequeue, затем от отправки успешного heartbeat). Выполнение отменяется с причиной `HeartbeatLost` по таймеру, когда до `validUntil` остаётся `HeartbeatInterval`, независимо от вызова heartbeat (§6.2). Нет успешного heartbeat дольше `LeaseDuration − HeartbeatInterval` → выборка на паузе, задачи, возвращённые in-flight dequeue'ем, не запускаются. **Исходы отправляются** (их защищает fencing по `lease_id`); остановка по `HeartbeatLost` тратит попытку (путь retry, §5.2). Отбрасывается только исход подтверждённо потерянного lease | Отмена до истечения своего lease не даёт задаче выполняться параллельно на другом поде — в том числе задаче, взятой после снимка последнего успешного heartbeat или in-flight dequeue'ем во время сбоя: общий таймер на сервер их не защищает. Трата попытки не даёт задаче, которая сама роняет heartbeat (исчерпание общего пула `NpgsqlDataSource`, голодание thread pool), возвращаться бесконечно. Отправка исходов не даёт задачам зависнуть в Processing, если БД вернулась до истечения lease |
| Распределение общего пула | Строгий порядок объявления очередей; минимум для очереди гарантирует её `Reserved` | Предсказуемо, одна выборка на очередь за итерацию. Голодание очереди без `Reserved` — осознанный выбор пользователя. Стратегия распределения внутренняя и заменяемая (веса — часть 3b) |
| Архитектура исполнения | Один диспетчер на виртуальный сервер; слоты — счётчики, выполнение — `Task` на задачу | Минимум запросов (`@n` = свободные слоты), строгий порядок, `Reserved`/`MaxConcurrency` и будущая стратегия выборки живут в одном месте. Воркер-цикл на слот (как в Hangfire) даёт N×poll в простое и не пакетирует dequeue |
| Hosted service | Один координирующий `IHostedService` на процесс, владеющий всеми виртуальными серверами | Хост останавливает hosted services последовательно (`ServicesStopConcurrently = false` по умолчанию): пока один сервер ждёт свои задачи, другой продолжал бы брать новые и получил бы лишь остаток `HostOptions.ShutdownTimeout`. `AddHostedService` дедуплицирует по типу реализации — второй сервер того же типа молча потерялся бы |
| Retry по умолчанию | `min(15 с × 2^(attempt−1), 1 ч)` ± 20 % jitter | При `MaxAttempts = 10`: 15 с, 30 с, 1, 2, 4, 8, 16, 32 мин, 1 ч — около 2 ч до `Failed`. Jitter растаскивает повторы после сбоя внешнего сервиса |
| Shutdown | Задача, остановившаяся по shutdown-токену (он сработал первым), возвращается в очередь **без траты попытки**; in-flight dequeue остановкой не отменяется, взятые им после сигнала задачи сразу возвращаются, тоже без траты попытки. Других путей возврата без траты попытки нет: остановка по `HeartbeatLost` — путь retry | Деплои не должны приводить долгие задачи к `Failed`. Задача, не уложившаяся в `ShutdownTimeout`, бросается, и попытку засчитывает sweeper — защита от бесконечного возврата |
| Таймаут выполнения | Опциональный: `[Job(TimeoutSeconds)]` и `DefaultJobTimeout` сервера. **По умолчанию таймаута нет** | Дефолтный таймаут молча убивает легитимные долгие задачи (опыт Hangfire) |

## 3. Публичный API

### 3.1 Регистрация сервера

```csharp
services.AddPgBolt(o => { ... });                     // core §6.3: клиент, схема, registry

services.AddPgBoltServer("orders", s =>               // один вызов = один виртуальный сервер
{
    s.Workers = 20;                                   // общий пул
    s.Queue("critical", q => q.Reserved = 5);         // порядок объявления = приоритет в общем пуле
    s.Queue("default");
    s.Queue("emails", q =>
    {
        q.MaxConcurrency = 4;
        q.MaxPollInterval = TimeSpan.FromSeconds(2);
    });

    s.LeaseDuration     = TimeSpan.FromSeconds(60);
    s.HeartbeatInterval = TimeSpan.FromSeconds(15);
    s.ShutdownTimeout   = TimeSpan.FromSeconds(25);
    s.DefaultJobTimeout = null;
    s.RetryPolicy = RetryPolicy.Exponential(TimeSpan.FromSeconds(15), TimeSpan.FromHours(1), jitter: 0.2);
    s.AddFilter<AuditFilter>();
});

services.AddPgBoltJobFilter<TracingFilter>();         // глобальный фильтр: для всех серверов процесса

services.ConfigurePgBoltProcessing(p =>               // необязательно; общее на процесс
{
    p.RunMaintenance   = true;
    p.PromoterInterval = TimeSpan.FromSeconds(1);
    p.SweeperInterval  = TimeSpan.FromSeconds(15);
});
```

- `AddPgBoltServer` требует предварительного `AddPgBolt` (иначе `InvalidOperationException` при регистрации). Имя сервера уникально в процессе и валидируется; `server_id` генерируется заново при каждом старте (`Guid.CreateVersion7()`).
- `ConfigurePgBoltProcessing`: `PromoterInterval` и `SweeperInterval` — > 0 и ≤ 1 сут (верхняя граница — как у длительностей §3.2); по умолчанию 1 с и 15 с (§6.3). `QueueSettingsRefreshInterval` (часть 3b) — интервал обновления настроек очередей процесса (какие очереди лимитированы, веса): по умолчанию 10 с, jitter ±10 %, > 0 и ≤ 1 сут; работает при любом `RunMaintenance`.
- `AddPgBoltServer` добавляет в DI описание сервера (имя + опции), а не hosted service. Единственный hosted service — `PgBoltProcessingService` (§4.1) — регистрируется первым вызовом `AddPgBoltServer`, повторные вызовы его не дублируют.

### 3.2 `PgBoltServerOptions`

| Свойство | По умолчанию | Валидация |
|---|---|---|
| `Workers` | `Environment.ProcessorCount * 2` | ≥ 0; `Workers + Σ Reserved ≥ 1` |
| `Queue(name, configure?)` | — | ≥ 1 очередь; имена уникальны в сервере |
| `LeaseDuration` | 60 с | > 0; ≤ 1 сут |
| `HeartbeatInterval` | 15 с | > 0; ≤ `LeaseDuration / 3` (отсюда ≤ 8 ч) |
| `ShutdownTimeout` | 25 с | ≥ 0; ≤ 1 сут |
| `DefaultJobTimeout` | `null` (нет) | `null` или > 0 и ≤ 2³² − 2 мс (≈ 49,7 сут) |
| `RetryPolicy` | `Exponential(15 с, 1 ч, 0.2)` | не `null` |
| `AckBatchSize` | 100 | ≥ 1 |
| `AckFlushInterval` | 20 мс | > 0; ≤ 1 сут |
| `AddFilter<T>()` | — | `T : class, IJobFilter` |

**Верхние границы длительностей.** Каждая длительность из опций становится задержкой таймера .NET (`Timer`, `CancellationTokenSource(delay, TimeProvider)`, `Task.Delay`, `Task.WaitAsync`), а они бросают `ArgumentOutOfRangeException` при задержке больше 2³² − 2 мс ≈ 49,7 сут — внутри runtime, а не при старте (например, при `LeaseDuration` в 60 сут не отправился бы ни один исход: каждая попытка падала бы на создании токена бюджета). Поэтому валидация ограничивает их сразу: интервалы (`LeaseDuration`, `ShutdownTimeout`, `AckFlushInterval`, `MaxPollInterval` §3.3, интервалы обслуживания §3.1) — 1 сут, с запасом на jitter (×1,1 у polling и heartbeat, ×1,2 у обслуживания); lease или опрос реже суток бессмысленны. `HeartbeatInterval` отдельной границы не требует (≤ `LeaseDuration / 3` ≤ 8 ч), с ним ограничены и производные таймауты ниже. `DefaultJobTimeout` — таймаут задачи, поэтому ограничен самим пределом таймера 2³² − 2 мс. Таймаут `[Job(TimeoutSeconds)]` при старте не проверяется — §3.5, §5.1.

Производные внутренние таймауты (не настраиваются): dequeue — `HeartbeatInterval` (§4.3), вызов heartbeat — `HeartbeatInterval / 2` (§6.2), бюджет повторов исхода — `LeaseDuration` (§6.1).

### 3.3 `QueueOptions`

| Свойство | По умолчанию | Смысл | Валидация |
|---|---|---|---|
| `Reserved` | 0 | Слоты, доступные только этой очереди | ≥ 0 |
| `MaxConcurrency` | `null` (нет) | Потолок одновременных задач очереди на этом сервере (reserved + общие) | `null` или ≥ `max(1, Reserved)` |
| `MinPollInterval` | 50 мс | Нижняя граница адаптивного polling | > 0 |
| `MaxPollInterval` | 10 с | Верхняя граница; определяет худшую межподовую задержку в простое | ≥ `MinPollInterval`; ≤ 1 сут (§3.2) |
| `ClusterMaxConcurrency` | `null` (нет) | Значение по умолчанию кластерного лимита: сколько задач очереди одновременно держат lease во всём кластере; переопределение через `IQueueSettingsManager` приоритетнее (часть 3b) | `null` или ≥ 1; одно значение у очереди на всех серверах процесса |
| `Weight` | `null` (нет) | Значение по умолчанию веса очереди в общем пуле — настройка очереди на кластер; переопределение через `IQueueSettingsManager` приоритетнее (часть 3b) | `null` или 1…1000; одно значение у очереди на всех серверах процесса |

`QueueOptions` — объект, а не параметры метода: опции добавляются без ломки API.

Ёмкость сервера `capacity = Workers + Σ Reserved` публикуется в `servers.capacity`.

### 3.4 Retry

```csharp
public abstract class RetryPolicy
{
    /// <returns>Задержка до следующей попытки; null — не повторять.</returns>
    public abstract TimeSpan? GetDelay(int attempt, Exception error);

    public static RetryPolicy Exponential(TimeSpan baseDelay, TimeSpan maxDelay, double jitter);
    public static RetryPolicy Custom(Func<int, Exception, TimeSpan?> getDelay);
}
```

- `Exponential`: `min(baseDelay × 2^(attempt−1), maxDelay) × (1 + U(−jitter, +jitter))`; `jitter ∈ [0, 1)`; `0 < baseDelay ≤ maxDelay`. Потолок применяется до умножения: если `attempt − 1 ≥ log2(maxDelay / baseDelay)`, сразу берётся `maxDelay` (без переполнения `TimeSpan` при больших `attempt`). Jitter применяется после потолка: фактическая задержка лежит в `maxDelay × (1 ± jitter)`.
- Порядок выбора задержки: `retry_delays` задачи (`RetryDelaysSeconds` или `EnqueueOptions.RetryDelays`; элемент `[attempt−1]`, при нехватке повторяется последний) → `RetryPolicy` сервера. Пустой массив `retry_delays` равнозначен его отсутствию.
- `attempt` — номер завершившейся попытки (1-based, как в `JobContext.Attempt`).
- Для NoExecutor (§5.2) `error` — `JobExecutorNotFoundException` (публичный тип `PgBolt.Server`, содержит имя типа задачи). `null` от политики → окончательный fail с `kind = NoExecutor`.
- Исключение из `GetDelay` — лог, задача обрабатывается как при `null` (окончательный fail).

### 3.5 Изменения `PgBolt.Abstractions`

- `JobAttribute.TimeoutSeconds` (`int`, по умолчанию `0` = нет таймаута; атрибут не допускает `int?`). Генератор проверяет значение: < 0 — ошибка BOLT007; > 4294967 (больше предела таймеров .NET 2³² − 2 мс = 4294967,294 с ≈ 49,7 сут) — предупреждение BOLT008: такой таймаут сервер урезает до предела (§5.1). Предупреждение, а не ошибка: код остаётся рабочим, а 49,7 сут против номинальных до ≈ 68 лет на практике не отличаются. Таймаут — свойство **типа задачи**: задаётся в `[Job]` на args-типе (обычно в сборке контрактов), а применяет его исполняющий сервер по своему registry (§5.1). В `job_types` не публикуется: он нужен только исполняющей стороне, enqueue и dashboard его не используют.
- `JobDescriptor` — позиционный public record; поле добавляется init-свойством `public int TimeoutSeconds { get; init; }` (по умолчанию `0`), а не позиционным параметром, чтобы не ломать конструктор. Генератор заполняет его из `[Job]`; `SameAs` сравнивает и `TimeoutSeconds`.
- `JobAbortedException(string message, Exception? inner = null)` — задача сообщает, что повтор бессмысленен; исход — окончательный `Failed`.
- `JobArgumentsException` — ошибка десериализации аргументов; бросается invoker'ом (§5.1), пользователю не нужна, но публична для фильтров.

### 3.6 Фильтры выполнения

> Пересмотрено в части 7a: OpenTelemetry-инструментирование не встраивается фильтром — consumer-span, метрики и логи выполнения живут в `JobRunner`, потому что фильтр создаётся в scope на каждую задачу и не видит исход (retry / fail / release), отказ «нет исполнителя» и shutdown (`2026-10-16-pgbolt-observability-design.md`, §2, §3.3).

```csharp
public delegate ValueTask JobExecutionDelegate();

public interface IJobFilter
{
    ValueTask InvokeAsync(JobExecutingContext context, JobExecutionDelegate next);
}

public sealed class JobExecutingContext
{
    public JobContext Job { get; }
    public IServiceProvider Services { get; }          // scope задачи
    public ReadOnlyMemory<byte> ArgsUtf8 { get; }
    public CancellationToken CancellationToken { get; }
}
```

- Типы фильтров регистрируются как scoped и резолвятся из scope задачи.
- Порядок: глобальные (`AddPgBoltJobFilter<T>()`) в порядке регистрации, затем фильтры сервера в порядке регистрации; первый зарегистрированный — внешний.
- Фильтр может выполнить код до и после `next`, перехватить или заменить исключение, не вызывать `next` (задача считается успешной).
- Исключение фильтра — исключение задачи (§5.2).
- `ArgsUtf8`: `LeasedJob.ArgsJson` в core — строка; runner перекодирует её в UTF-8 один раз на задачу (`Encoding.UTF8.GetBytes`), тот же буфер получают фильтры и invoker. Чтение `args` из dequeue сразу байтами — кандидат оптимизации части 7 по бенчмарку.

## 4. Компоненты

### 4.1 Состав

**На процесс** — единственный `IHostedService` `PgBoltProcessingService` (координатор). Владеет всеми виртуальными серверами, `ProcessingMaintenance` (promoter и sweeper, §6.3) и общим `IWakeupSignal` из core. Запуск — §4.4, остановка — §6.4.

**На виртуальный сервер** — `PgBoltServer` (не hosted service), владеющий:

| Компонент | Ответственность |
|---|---|
| `SlotAllocator` | Счётчики занятых слотов по очередям; выдаёт план `[(queue, n)]` (§4.2) |
| `IFetchStrategy` (internal) | `FetchAsync(queue, n, ct) → LimitedDequeueResult(Jobs, LimitReached)`. Одна реализация: очереди из снимка лимитированных очередей `QueueSettingsCache` — `PgBoltStore.DequeueLimitedAsync` (часть 3b §6.2), остальные — `DequeueAsync` (core §5.2) с `LimitReached = false`; снимок читается при каждом вызове |
| `Dispatcher` | Fetch-цикл (§4.3) |
| `JobRunner` | Выполнение одной задачи и классификация исхода (§5) |
| `CompletionSink` | Отправка исходов: ack пакетно, остальное поштучно, с повтором (§6.1) |
| `LeaseKeeper` | Таблица выполнений, heartbeat, проверка срока lease каждого выполнения, отмена, потерянные lease (§6.2) |

Все таймеры идут через `TimeProvider` (зарегистрирован core); интервалы измеряются монотонно (`TimeProvider.GetTimestamp`), а не по wall clock. Доступ к БД — через внутренний интерфейс над `PgBoltStore`, чтобы runtime тестировался без PostgreSQL.

### 4.2 Слоты и план выборки

- Задача очереди занимает свободный `Reserved`-слот своей очереди, иначе — общий слот. При освобождении возвращается слот того же вида.
- `MaxConcurrency` ограничивает очередь целиком (reserved + общие).
- План на итерацию строится в порядке объявления очередей. Для каждой очереди, у которой наступил `nextPoll`: `n = min(свободные Reserved + свободные общие, MaxConcurrency − занято)`. Очередь с `n = 0` в план не попадает (`DequeueAsync` не принимает `max ≤ 0`), её `nextPoll` не меняется. Общие слоты, которые очередь не добрала фактическим dequeue, в той же итерации переходят к следующим очередям (план пересчитывается после каждого dequeue).
- Распределение общего пула — внутренняя стратегия `SlotAllocator` (`ISharedPoolDistribution`): без эффективных весов у очередей сервера — строгий порядок объявления, с весом хотя бы у одной — `WeightedDistribution` (часть 3b §7). `SlotAllocator` получает источник весов (снимок `QueueSettingsCache`) и на границе плана применяет его: изменился вектор весов сервера — новая стратегия; `Dispatcher` не меняется.
- **Бюджет плана.** Внутри плана общий пул ограничен остатком «свободные общие слоты на границе плана минус общие, взятые в этом плане»; слоты, освободившиеся посреди плана, в этом плане не раздаются и достаются следующему (диспетчер начинает его сразу по `slotFreed`). Без бюджета после пачки одновременно закончившихся задач план, начатый по первому освобождению, отдавал бы остальные слоты следующим записям мимо порядка и весов. `Reserved` бюджетом не ограничены; недобор очереди по-прежнему переходит к следующим записям плана; `Available(queue)` вне плана — фактический.
- План строит и выдаёт `SlotAllocator.Plan(isDue)` — ленивая последовательность `(queue, n)`: каждая запись вычисляется под lock allocator'а в момент запроса, то есть после `Take` по предыдущей записи, поэтому недобранные общие слоты переходят к следующим очередям без отдельного пересчёта в диспетчере. `isDue(queue)` — наступил ли `nextPoll` очереди; он вычисляется один раз на запись для всех очередей, и стратегия и проверка её ответа видят один и тот же набор. Каждая очередь попадает в план не больше одного раза; `n ≥ 1` (очередь с `n = 0` не выдаётся). Диспетчер не вычисляет `n` и не обходит очереди сам.
- Стратегия (`ISharedPoolDistribution`, по умолчанию строгий порядок объявления) на границе плана получает `BeginPlan`, затем кандидаток — очереди, которые готовы и ещё не выдавались в этом плане, — доступные слоты каждой (в пределах бюджета плана), свободные `Reserved` и бюджет общего пула, а возвращает следующую запись `(очередь, n)` или «план исчерпан». Allocator проверяет ответ: очередь должна быть кандидаткой, `1 ≤ n ≤ Available`. «План исчерпан» допустим, только когда ни у одной кандидатки нет свободного слота; иначе allocator бросает `InvalidOperationException`. Каждый `Take` сообщает стратегии `OnTaken`. Без этой проверки стратегия, закончившая план при готовой очереди со свободным слотом, дала бы диспетчеру нулевую задержку ожидания (§4.3) и холостой цикл; с ней пустой план всегда значит «ни у одной готовой очереди нет свободного слота», а ошибка стратегии обрабатывается как неожиданная ошибка итерации (§4.3) — с паузой.

### 4.3 Fetch-цикл `Dispatcher`

```
loop:
  for (queue, n) in allocator.Plan():              // порядок — стратегия общего пула (§4.2); запись вычисляется
                                                   // после Take по предыдущей; план ограничен бюджетом
      if stopping or leaseKeeper.HeartbeatLost: break
      fetchStartedAt = GetTimestamp()              // до открытия соединения
      jobs, limitReached = fetch(queue, n)         // таймаут HeartbeatInterval; токеном остановки не отменяется
      validUntil = fetchStartedAt + LeaseDuration  // результат получен после полного чтения reader'а (§6.2)
      if stopping or leaseKeeper.HeartbeatLost:    // взяты после сигнала остановки или во время сбоя —
          leaseKeeper.RegisterForRelease(jobs, validUntil)   // сразу OutcomePending с исходом release, ran = false;
          break                                    // не запускаются, слоты не занимаются (§6.2, §6.4, §7.1)
      if now > fetchStartedAt + HeartbeatInterval: // dequeue вернулся позже своего таймаута —
          leaseKeeper.RegisterForRelease(jobs, validUntil)   // тоже release с ran = false, без запуска
      else:
          leaseKeeper.Register(jobs, validUntil)   // состояние Running
          allocator.Take(queue, len(jobs)); start JobRunner для каждой
      limitReached   → interval = min(interval × 2, Max), nextPoll = now + interval × (1 ± 0.1)   // как пустой (часть 3b)
      len(jobs) == n → interval = Min, nextPoll = now            // очередь «горячая»
      len(jobs) == 0 → interval = min(interval × 2, Max), nextPoll = now + interval × (1 ± 0.1)
      иначе          → interval = Min, nextPoll = now + Min
  if stopping: exit
  применить флаги пробуждения                      // после обновления nextPoll по результатам dequeue
  ждать wake или ближайшего nextPoll очереди с n ≥ 1
```

**Пробуждение.** У диспетчера своё latched auto-reset событие `wake` и флаги по очередям:
- освобождение слота очереди `q` (`JobRunner`) → флаг `slotFreed[q]`, `wake.Set()`;
- `IWakeupSignal.Subscribe(q, …)` для каждой очереди сервера (§8.2) → флаг `signaled[q]`, `wake.Set()`;
- сигнал остановки и снятие паузы (§6.2) → `wake.Set()`;
- коммит исхода задачи очереди `q` (`CompletionSink`, колбэк `onLeaseFreed`, §6.1) → флаг `leaseFreed[q]`, `wake.Set()` (часть 3b).

`Set` без ожидающего сохраняет состояние до следующего ожидания, поэтому сигнал, пришедший между пустым dequeue и ожиданием (или во время dequeue), не теряется. Флаги применяются после обновления `nextPoll` по результатам dequeue: `signaled[q]` → `nextPoll = now`, `interval = Min`; `slotFreed[q]` → `nextPoll = now`. Пока у очереди установлен признак `LimitReached` последнего dequeue (кластерный лимит исчерпан, часть 3b §6.3), `signaled[q]` и `slotFreed[q]` поглощаются без изменения `nextPoll`, а `leaseFreed[q]` ставит `nextPoll = now`: место в лимите видно следующему dequeue только после коммита исхода; без признака `leaseFreed[q]` сбрасывается без действия. Ожидание — `Task.WhenAny(wake, delay до ближайшего nextPoll)` без токена на слот: освобождение слота не порождает исключений.

- Dequeue выполняется с собственным таймаутом `HeartbeatInterval` (токен с `CancelAfter`; покрывает и открытие соединения, и команду, не зависит от `Timeout`/`CommandTimeout` строки подключения). `now()` транзакции dequeue не раньше `fetchStartedAt`, поэтому `lease_until ≥ fetchStartedAt + LeaseDuration` по локальным монотонным часам — это начальный `validUntil` выполнения (§6.2). Таймаут гарантирует, что к моменту регистрации до `validUntil` остаётся не меньше `LeaseDuration − HeartbeatInterval ≥ 2 × HeartbeatInterval` (§3.2), то есть до рубежа отмены — не меньше `HeartbeatInterval`.
- **Таймаут не всегда срабатывает вовремя.** Отменяя команду в полёте, Npgsql сначала синхронно отправляет PostgreSQL CancelRequest через новое соединение (открытие с `Timeout` строки подключения, 15 с по умолчанию) и только потом рвёт своё; `Cancellation Timeout = -1` отменяет лишь ожидание ответа. Без сети вызов возвращается, когда сеть вернулась или CancelRequest упал по `Timeout`, — и может вернуть задачи: ответ statement'а, дошедший раньше разрыва, прочитан. Гарантия выше тогда не выполняется: выполнение сразу достигло бы рубежа отмены, отменилось бы с `HeartbeatLost` и потратило попытку. Поэтому задачи dequeue, вернувшегося позже `fetchStartedAt + HeartbeatInterval`, не запускаются, а регистрируются сразу в `OutcomePending` и уходят release с `ran = false` (§7.1) — как задачи, взятые во время сбоя heartbeat; предупреждение в лог. Прерывать ожидание самого вызова (`WaitAsync` на отдельном таймере) runtime не стал: dequeue продолжился бы в фоне, и его задачи пришлось бы отпускать из обработчика вне цикла, в гонке с остановкой (§6.4 ждёт in-flight dequeue); во время сбоя сети новый dequeue всё равно не прошёл бы, а длительность ожидания ограничена `Timeout` CancelRequest'а.
- Проверка `stopping` и «heartbeat потерян» после fetch и старт `JobRunner` не атомарны. Если сигнал остановки пришёл между ними, runner видит уже отменённый shutdown-токен (его токен связан с общим CTS сервера, §5.1) и возвращает задачу release, не вызывая исполнитель. Если сбой heartbeat начался между ними, выполнение отменит проверка срока lease (§6.2) — по его собственному `validUntil`.
- Ошибка dequeue (включая таймаут) → лог, пауза сервера с backoff 1 → 30 с; цикл не падает. Если statement успел закоммититься, взятые строки runtime не известны: heartbeat их не продлевает (§6.2), они истекают, sweeper засчитывает попытку — как при падении процесса. Явный release таких «сиротских» строк не делается: без знания, какой dequeue ещё в полёте, он гонится с регистрацией.
- **Неожиданная ошибка итерации** (не ошибка dequeue): исключение регистрации, учёта слотов, запуска выполнения, постановки release в `CompletionSink` или стратегии плана (в том числе нарушение её контракта, §4.2) → лог уровня Critical и та же пауза сервера 1 → 30 с; цикл не падает. Иначе выборка молча остановилась бы при живом heartbeat. Исключение `IWakeupSignal.Subscribe` пользовательской реализации → лог, очередь опрашивается без сигналов (polling её страхует); исключение `Dispose` подписки → лог.
- **Откат незапущенного выполнения.** Если после регистрации задачи как `Running` взятие слота или запуск `JobRunner` бросает, диспетчер до передачи исключения обработчику итерации сначала снимает запись (CAS `Running → Removed`, удаление из таблицы `LeaseKeeper`), затем возвращает слот и пишет предупреждение. Иначе запись осталась бы `Running` навсегда: исход её никто не сдаст, а heartbeat продлевал бы её lease, пока жив процесс (нарушение критерия §1). Запись снимается первой, потому что снятие не бросает, а возврат слота бросает при ошибке учёта — такая ошибка пишется в лог и не мешает откату и передаче исходного исключения. После отката lease истекает не позже `validUntil`, sweeper засчитывает попытку, поэтому даже постоянный сбой запуска заканчивается исчерпанием попыток. Остальные задачи того же пакета не регистрируются: это сиротские строки, их забирает sweeper. Запуск выполнения либо стартует задачу, либо бросает, не стартовав её (старт `Task` — последнее действие), поэтому откат не снимает работающее выполнение.
- Проверка `stopping`/«heartbeat потерян» выполняется **до** регистрации: задача регистрируется либо как `Running` (и запускается), либо сразу как `OutcomePending` с исходом release — промежуточного состояния «зарегистрирована как `Running`, но не запущена» нет.
- Пока `LeaseKeeper` в состоянии «heartbeat потерян» (§6.2), новые dequeue не начинаются; задачи, которые вернул dequeue, начатый до сбоя, регистрируются сразу в `OutcomePending` и отправляются release с `ran = false` (§7.1): они не выполнялись, попытка не засчитывается.
- Воркер никогда не держит транзакцию дольше одного round trip'а: лимитированный dequeue (`pg_advisory_xact_lock` и dequeue одним батчем в неявной транзакции, часть 3b §6.2) ничего не блокирует надолго.

### 4.4 Старт (`PgBoltProcessingService.StartAsync`)

1. Дождаться `PgBoltInitializer.Ready` (миграции, изоляция, партиции; §8.3). Координатор ждёт её явно, а не полагается на порядок регистрации hosted services; ошибка или отмена `Ready` — ошибка старта.
2. Опубликовать `job_types` (`PublishJobTypesAsync`, core §4.5) — один раз на процесс, `published_by = $"{Environment.MachineName}/{Environment.ProcessId}"`: registry — свойство процесса, а не виртуального сервера. Проверка расхождения схем (`published_by <> @published_by`, `PgBoltStore.JobTypes.cs`) считает «другим публикатором» любой другой процесс; с одним `MachineName` она не видела бы конфликт двух процессов на одном хосте (например, два приложения с разными версиями контрактов в одной VM). PID, повторно выданный перезапущенному процессу (в контейнере — обычно 1), безопасен: прежний процесс с тем же идентификатором уже не работает, его запись перезаписывается.

   Затем (часть 3b) синхронизировать значения по умолчанию кластерного лимита и веса очередей всех серверов процесса (`SyncQueueDefaultsAsync`, Warning при расхождении с недавно стартовавшим процессом) и загрузить настройки очередей в `QueueSettingsCache` (часть 3b §4.2) — до создания серверов: стратегия выборки и первый план каждого диспетчера уже видят лимиты и веса. Разные `ClusterMaxConcurrency` или `Weight` одной очереди на серверах процесса — ошибка старта.
3. Для каждого сервера: зарегистрировать его (`INSERT INTO servers`, §7.2).
4. Предупреждение в лог (на сервер): в `job_types` есть типы с `default_queue` из очередей сервера, для которых у процесса нет исполнителя (такие задачи уйдут в NoExecutor, core §5.4). Это оценка по умолчаниям: задача, поставленная в очередь явным `EnqueueOptions.Queue`, сюда не попадает.
5. Предупреждение (одно на процесс), если `max(ShutdownTimeout серверов) + AckFlushInterval + 2 с > HostOptions.ShutdownTimeout`. Серверы останавливаются параллельно (§6.4), поэтому таймауты не суммируются.
6. Запустить цикл обновления `QueueSettingsCache` (при любом `RunMaintenance`), затем `ProcessingMaintenance` (если включено), затем для каждого сервера `LeaseKeeper` и `Dispatcher`.

Регистрация всех серверов (п. 3–4) завершается до запуска любого (п. 6): ошибка регистрации любого сервера роняет старт до того, как хоть один сервер начал брать задачи. Хост не вызывает `StopAsync` после ошибки `StartAsync`, поэтому задачи, взятые в этом окне, оборвались бы при выходе процесса, и sweeper засчитал бы попытку.

Ошибка шагов 1–3 роняет старт хоста с понятным сообщением. Строки `servers`, уже вставленные до ошибки, убирает уборка части 2. Ошибка шага 6 (последний рубеж: запуск компонентов синхронный и на практике не бросает) — лог уровня Critical, остановка всего уже запущенного (§6.4) и ошибка старта.

## 5. Выполнение задачи

### 5.1 `JobRunner`

1. Если shutdown-токен сервера уже отменён (сигнал остановки пришёл после проверки `stopping` в диспетчере, §4.3) — release с `ran = false` (§7.1), исполнитель не ищется и не вызывается.
2. Найти исполнителя в `JobRegistry` по `type`. Не найден → путь NoExecutor (§5.2), без scope.
3. Создать `AsyncServiceScope`.
4. Связанный `CancellationTokenSource` из источников; runner запоминает, какой сработал первым. Shutdown-токен — общий `CancellationTokenSource` сервера: отменённый до создания связанного источника, он сразу делает связанный токен отменённым, поэтому задача, стартовавшая после отмены (между п. 1 и вызовом), получает `OperationCanceledException` при первой проверке токена и уходит в release (§5.2 п. 4).
   - **Shutdown** — остановка процесса (§6.4);
   - **CancelRequested** — отмена, доставленная heartbeat'ом (§6.2);
   - **HeartbeatLost** — подозрение на потерю lease: продление lease этого выполнения не подтверждено, до `validUntil` осталось `HeartbeatInterval` (проверка срока lease, §6.2);
   - **LeaseLost** — подтверждённая потеря lease (§6.2);
   - **Timeout** — `CancelAfter(timeout)`, где `timeout = TimeoutSeconds задачи > 0 ? … : DefaultJobTimeout` (нет обоих — не ставится). `TimeoutSeconds` берётся из `JobDescriptor` исполнителя в registry процесса. `DefaultJobTimeout` уже ограничен пределом таймеров .NET 2³² − 2 мс (§3.2), а `TimeoutSeconds` больше него (`int` допускает до ≈ 68 лет) **урезается до 2³² − 2 мс** (≈ 49,7 сут): иначе создание токена бросило бы `ArgumentOutOfRangeException` мимо классификации исхода, и выполнение осталось бы `Running` с занятым слотом. Старт сервера такой тип задачи не роняет: он задаётся в сборке контрактов и может выполняться многими хостами. Урезание не молчаливое: для `[Job]` генератор предупреждает BOLT008 при компиляции (§3.5), а runner при первом урезании таймаута типа задачи пишет предупреждение в лог (один раз на тип задачи в сервере) — это покрывает и дескриптор, зарегистрированный вручную в обход генератора. В сообщение `timeout after N s` (§5.2) идёт урезанное значение.
5. Собрать `JobContext` (core §6.1) и вызвать конвейер фильтров → invoker.
6. Invoker (`JobsBuilder` в `PgBolt.Postgres`, §8.4) оборачивает исключение десериализации (`JsonException`, `NotSupportedException` от STJ, `null` вместо объекта) в `JobArgumentsException`. Исключения самой задачи не оборачиваются.
7. Классифицировать исход (§5.2), передать его в `CompletionSink` (переход записи `Running → OutcomePending`, §6.2), освободить слот. Слот освобождается сразу, не дожидаясь отправки исхода; выполнение остаётся в таблице `LeaseKeeper` до завершения отправки (§6.1). Если запись уже `Removed` (выполнение брошено при остановке или lease подтверждённо потерян), исход отбрасывается с логом (§6.1).

Если задача не реагирует на отмену (shutdown, отмена, таймаут, потеря lease), слот остаётся занятым, а выполнение — в таблице `LeaseKeeper` (задача фактически выполняется, её lease продлевается, кроме подтверждённо потерянного); раз в `HeartbeatInterval` пишется предупреждение с id задачи и временем с момента отмены. Прервать `Task` в .NET нельзя.

| 4 | `OperationCanceledException`, первым сработал `Shutdown` | Release без траты попытки | §7.1, `ran = true` |
| 5 | `JobAbortedException` или `JobArgumentsException` | Окончательный fail | core §5.4, `state = 3`, `kind = Failed` |
| 6 | Любое другое исключение, включая: исключение после `Shutdown`, отличное от `OperationCanceledException`; отмену по `Timeout` — с сообщением `timeout after N s`; любое исключение после `HeartbeatLost` (в том числе `OperationCanceledException` и последовавший за `HeartbeatLost` shutdown) — с сообщением `cancelled: lease renewal not confirmed` | `delay` по §3.4; `attempt < max_attempts` и `delay ≠ null` → retry, иначе окончательный fail | core §5.4 |
| — | Исполнитель не найден | `delay` по §3.4 с `JobExecutorNotFoundException`; `attempt < max_attempts` и `delay ≠ null` → retry с `kind = NoExecutor`; иначе окончательный fail с `kind = NoExecutor` | core §5.4 |

- `HeartbeatLost` — только подозрение: исход отправляется, его корректность обеспечивает fencing по `lease_id` (core §5.3). Если lease на самом деле уже забран, statement затронет 0 строк.
- Остановка по `HeartbeatLost` **тратит попытку** (путь retry core §5.4, как у sweeper'а), release здесь не применяется. Причина heartbeat может быть в самой задаче: она исчерпывает общий пул `NpgsqlDataSource` (общий с приложением при `o.DataSource`) или голодит thread pool, heartbeat не получает соединение за `HeartbeatInterval / 2`, выполнение отменяется. Release с прежним `attempt` возвращал бы такую задачу бесконечно, и она никогда не дошла бы до `Failed`; release без декремента при `attempt = max_attempts` дал бы следующему dequeue `attempt > max_attempts`. Путь retry учитывает `max_attempts`, `retry_delays`/`RetryPolicy` (backoff полезен при перегрузке БД) и пишет событие. `error` для `RetryPolicy` — исключение задачи.
- Правило «запрошена отмена → Cancelled» обеспечивает SQL core на любом пути освобождения lease; runner его не дублирует. Успех, завершившийся раньше доставки отмены, фиксируется как Succeeded (core §5.7).
- В `job_events` пишутся `message` (сообщение исключения) и `exception` (`Exception.ToString()`), каждое обрезано до 8 КБ — 8192 байт в UTF-8 (так строка хранится в PostgreSQL; обрезка по 8192 символам давала бы до 16–24 КБ для кириллицы и CJK), по границе кодовой точки, без разрыва суррогатной пары. Одиночные суррогаты (невалидный UTF-16 из пользовательского кода) до обрезки заменяются на U+FFFD: Npgsql кодирует строки строгим UTF-8, и такой исход не отправился бы ни разу.

## 6. Исходы, lease, обслуживание

### 6.1 `CompletionSink`

- **Ack:** буфер `LeaseRef`, сброс при `AckBatchSize` элементов или через `AckFlushInterval` после первого элемента. Затронуто строк меньше, чем в пакете → lease остальных потерян, лог (core §9).
- **Retry / fail / confirm-cancel / release:** поштучные statement'ы, параллельно.
- **`onLeaseFreed`** (необязательный колбэк конструктора, часть 3b): вызывается с очередью выполнения при успешном переходе записи `OutcomeInFlight → Removed` — после коммита statement'а исхода (ack-пакет — для каждой записи), когда место в кластерном лимите видно следующему dequeue. `PgBoltServer` передаёт `Dispatcher.OnLeaseFreed`.
- **Приём исхода** — только через переход записи выполнения `Running → OutcomePending` (§6.2). Исход выполнения, которого уже нет в таблице `LeaseKeeper` (`Removed`: брошено при остановке, lease подтверждённо потерян), и исход, пришедший после остановки `CompletionSink` (§6.4 п. 5), отбрасываются с логом: lease такой задачи больше не держится, ею займётся sweeper или новый владелец. Так брошенная задача, завершившаяся позже, не отправит исход.
- **Отправка:** перед каждым statement'ом (и каждым повтором) sink атомарно переводит запись `OutcomePending → OutcomeInFlight`; не удалось (запись `Removed`) — отправка прекращается. После ответа: успех или `LeaseLost` → `Removed`; ошибка → `OutcomeInFlight → OutcomePending` и повтор. Ack-пакет переводит так каждую свою запись.
- **Повтор.** `DbRetry` core повторяет внутри вызова только 40P01/40001. Любую другую ошибку отправки (сеть, таймаут, отказ пула, отсутствующая партиция `job_events`) повторяет `CompletionSink` с backoff 100 мс → 5 с. Пока исход не отправлен, выполнение остаётся в таблице `LeaseKeeper` (состояние «исход ждёт отправки»), и heartbeat продолжает держать его lease. Повтор заканчивается:
  - успехом;
  - ответом БД о потере lease (0 строк, `LeaseLost`). После неоднозначной ошибки (statement мог закоммититься) это ожидаемо и пишется в лог как «исход, вероятно, уже применён»: fencing не даёт применить исход дважды;
  - подтверждённой потерей lease по heartbeat (§6.2 п. 5): heartbeat переводит запись `OutcomePending → Removed`, а пока statement в полёте (`OutcomeInFlight`), запись не трогает — авторитетен результат statement'а;
  - исчерпанием бюджета `LeaseDuration` с первой попытки → лог уровня Error, запись `OutcomePending → Removed`, выполнение удаляется из таблицы. Heartbeat перестаёт его продлевать, lease истекает не позже чем через `LeaseDuration`, sweeper засчитывает попытку (at-least-once сохраняется; бесконечного продления брошенной строки нет);
  - дедлайном остановки (§6.4).
- **Таймаут попытки** — остаток бюджета: каждая попытка (ack-пакет — по минимальному остатку своих записей) ограничена `LeaseDuration − (время с первой попытки)` независимо от того, соблюдает ли вызов токен (TCP black hole, `Command Timeout=0`); последняя пауза backoff урезается до конца бюджета. Так зависшая попытка не держит запись в `OutcomeInFlight` — а с ней и продление lease heartbeat'ом — дольше бюджета, и запись покидает таблицу не позже `LeaseDuration` с первой попытки. Брошенный вызов может завершиться в фоне: fencing по `lease_id` не даёт применить исход после того, как lease забрал sweeper.
- Release задачи, не запускавшейся (§4.3), поставленный после остановки sink, тоже отбрасывается с логом (запись `OutcomePending → Removed`): его отправку уже никто не ждал бы.
- Остановка, прерванная токеном хоста (§6.4): отправки и паузы прерываются, записи переводятся в `Removed` и удаляются из таблицы с логом. Ack, принятые в буфер после последнего сброса, пока остановка ждала отправки, тоже не отправляются, а отбрасываются так же — не остаются в таблице без отправки.
- Подозрение на потерю lease («heartbeat потерян», §6.2) отправку не останавливает: если БД вернулась до истечения lease, исход проходит, и задача не зависает в Processing.
- После завершения отправки (любым из путей выше) выполнение удаляется из таблицы `LeaseKeeper`.

### 6.2 `LeaseKeeper`

**Таблица выполнений** `lease_id → (job_id, CancellationTokenSource, state, validUntil)`, `state ∈ {Running, OutcomePending, OutcomeInFlight, Removed}`. Задача регистрируется до запуска `JobRunner`, сразу после полного чтения результата dequeue: `PgBoltStore.DequeueAsync` возвращает список только после прочтения reader'а до конца (ReadyForQuery), поэтому к моменту регистрации statement dequeue закоммичен. Задачи, которые не будут запускаться (§4.3), регистрируются сразу в `OutcomePending` с исходом release.

`validUntil` — нижняя граница `lease_until` выполнения по локальным монотонным часам (`TimeProvider.GetTimestamp`): при регистрации `fetchStartedAt + LeaseDuration` (§4.3), после каждого успешного heartbeat, вернувшего этот lease, — `max(validUntil, sentAt + LeaseDuration)`.

**Переходы состояния** атомарны (CAS по полю состояния записи): переход выполняется, только если текущее состояние совпало с ожидаемым; иначе вызывающий видит фактическое состояние и действует по нему.
- `Running → OutcomePending` — runner сдаёт исход (§5.1 п. 7);
- `OutcomePending → OutcomeInFlight` — sink перед отправкой statement'а; `OutcomeInFlight → OutcomePending` — ошибка отправки, перед повтором (§6.1);
- `Running | OutcomePending → Removed` — подтверждённая потеря по heartbeat (п. 5), выполнение брошено при остановке (§6.4 п. 3), исчерпан бюджет отправки (§6.1);
- `OutcomeInFlight → Removed` — только sink, по результату statement'а (успех или `LeaseLost`).

`Removed` терминально; запись с ним удаляется из таблицы. Благодаря CAS решение heartbeat «потерян, если исход не в полёте» не гонится с началом отправки: либо sink успел перевести запись в `OutcomeInFlight` (heartbeat её не трогает), либо heartbeat перевёл её в `Removed` (sink не начнёт statement).

**Heartbeat-цикл.** Расписание отсчитывается от `sentAt` предыдущего вызова, а не от его завершения: следующий `sentAt = предыдущий sentAt + HeartbeatInterval × (1 ± 0.1)`. Вызовы не перекрываются: таймаут вызова `HeartbeatInterval / 2` меньше минимального шага `0.9 × HeartbeatInterval`. Так медленный, но успешный вызов не сдвигает расписание: при последнем успехе в `S` следующий успешный ответ приходит не позже `S + 1.1 HI + 0.5 HI = S + 1.6 HI`, раньше рубежа «heartbeat потерян» `S + LeaseDuration − HI ≥ S + 2 HI` (§3.2), и ложного `HeartbeatLost` при живой БД нет. При минимально допустимом `LeaseDuration = 3 × HeartbeatInterval` один неудачный вызов уже переводит сервер в «heartbeat потерян»; значения по умолчанию (60 с / 15 с) переживают два неудачных вызова подряд.

Шаги вызова:
1. `sentAt = TimeProvider.GetTimestamp()`; снимок `(job_id, lease_id)` всех записей таблицы.
2. `HeartbeatAsync(serverId, снимок, LeaseDuration)` (§8.1) с таймаутом `HeartbeatInterval / 2` (токен с `CancelAfter`; покрывает открытие соединения и команду, не зависит от `CommandTimeout`, в том числе от `0` = бесконечно).
3. Успех → `lastSuccess = sentAt`. Каждая строка ответа имеет `lease_until = now() БД + LeaseDuration`, а `now()` БД не раньше `sentAt`, поэтому для каждого `lease_id` из ответа `validUntil = max(validUntil, sentAt + LeaseDuration)`.
4. `cancel_requested = true` → отменить токен выполнения с причиной `CancelRequested`.
5. `lease_id` из снимка, отсутствующий в ответе и всё ещё в таблице, — lease **подтверждённо потерян**: CAS `Running | OutcomePending → Removed`; для `Running` — отменить токен с причиной `LeaseLost`, для `OutcomePending` — исход снимается. Запись в `OutcomeInFlight` не трогается: ack или fail того же сервера мог удалить или освободить строку раньше heartbeat, поэтому авторитетен результат statement'а. Выполнения, зарегистрированные после снимка, в нём отсутствуют и не проверяются (их dequeue мог закоммититься после снимка heartbeat, core §5.5).
6. Ошибка или таймаут → лог, следующий вызов по расписанию.

Таймаут `HeartbeatInterval / 2` без сети срабатывает не вовремя по той же причине, что и у dequeue (§4.3): отмена Npgsql ждёт CancelRequest, и вызов длится до возврата сети или до `Timeout` строки подключения. Корректность от этого не зависит: `lastSuccess` и `validUntil` считаются от `sentAt`, поэтому поздний успешный ответ безопасен (`now()` БД не раньше `sentAt`); «heartbeat потерян» и отмена выполнений идут по таймеру, а не по завершению вызова. Сдвигается только расписание: следующий вызов начинается сразу после затянувшегося (его `sentAt` уже прошёл), вызовы по-прежнему не перекрываются. Брошенные по таймауту вызовы без ожидания (`WaitAsync`) runtime не использует: каждый держал бы соединение пула и поток, заблокированный синхронной отправкой CancelRequest, и при малом `HeartbeatInterval` они копились бы на всё время сбоя.

Строки с `lease_owner = server_id`, которых нет в таблице («сиротские»: исход брошен по бюджету, dequeue закоммичен, но ответ не получен, выполнение брошено при остановке), не продлеваются и истекают — их обрабатывает sweeper.

**Проверка срока lease** — по каждому выполнению, а не одним таймером на сервер. Рубеж выполнения — `validUntil − HeartbeatInterval`. Таймер `TimeProvider` взводится на ближайший рубеж среди записей `Running` и перевзводится при регистрации, после успешного heartbeat и после срабатывания; он не зависит от того, завершился ли текущий вызов heartbeat. При срабатывании каждое выполнение `Running` с `now ≥ validUntil − HeartbeatInterval` отменяется с причиной `HeartbeatLost` (однократно; первенство причин — §5.1). До истечения его lease остаётся не меньше `HeartbeatInterval` — время остановиться, пока sweeper другого пода не отдал задачу повторно. Исходы не отбрасываются: `CompletionSink` продолжает отправку (§6.1), остановленная задача уходит по пути retry (§5.2).

Почему не один watchdog от `lastSuccess`: задача, чей dequeue начался в `t0` и длился почти `HeartbeatInterval`, может зарегистрироваться после снимка успешного heartbeat с `sentAt ≈ t0 + HeartbeatInterval`. Её lease действует до `t0 + LeaseDuration` — ровно момент срабатывания серверного watchdog'а (`sentAt + LeaseDuration − HeartbeatInterval`), запаса на остановку нет. По собственному `validUntil = t0 + LeaseDuration` она отменяется в `t0 + LeaseDuration − HeartbeatInterval`. Проверка идёт по таймеру всё время сбоя, а не однократно при переходе, поэтому покрывает и выполнения, начавшиеся после его начала.

**Состояние «heartbeat потерян»** (на сервер): `now ≥ lastSuccess + LeaseDuration − HeartbeatInterval`; до первого успешного heartbeat отсчёт ведётся от старта `LeaseKeeper` (раньше него lease у сервера нет). Пока оно действует:
- `Dispatcher` не начинает новые dequeue; задачи, которые вернул dequeue, начатый до сбоя (с медленной БД он укладывается в свой таймаут `HeartbeatInterval`, тогда как heartbeat обрывается по `HeartbeatInterval / 2`), не запускаются, а сразу уходят release с `ran = false` (§4.3, §7.1): они не выполнялись, декремент `attempt` корректен. Если release не пройдёт за бюджет `LeaseDuration`, lease истечёт и попытку засчитает sweeper;
- выполнения из снимка последнего успешного heartbeat достигают своего рубежа одновременно с входом в это состояние и отменяются проверкой срока lease; выполнения, зарегистрированные позже, — по своему `validUntil`.

Первый успешный heartbeat снимает состояние (пауза снимается, `wake.Set()`); подтверждённые потери определяются по п. 5. Уже отменённые выполнения не восстанавливаются. Lease из снимка, ещё не забранный sweeper'ом, продлевается снова — это безопасно: `lease_id` не изменился, значит, задачу никто не брал, а у выполнения есть ждущий исход или оно ещё выполняется.

**Строка `servers` (часть 2 §9.2).** Ответ heartbeat сообщает `ServerPresent`. При `false` `LeaseKeeper` внутри того же вызова (после обработки lease) выполняет upsert регистрации с таймаутом `HeartbeatInterval / 2` и токеном цикла; ошибка — Warning, повтор при следующем heartbeat. Граница «следующий успешный ответ не позже `S + 1.6 HI`» сохраняется; `StopAsync` дожидается идущей регистрации до удаления строк серверов, поэтому строка после остановки не воскресает.

### 6.3 `ProcessingMaintenance` (на процесс)

Запускается, если в процессе зарегистрирован хотя бы один сервер и `RunMaintenance = true`. Все поды выполняют оба цикла одновременно: `SKIP LOCKED` делает это безопасным без координации.

- **Promoter:** `PromoteDueAsync(1000)` (core §5.11), повтор, пока пакет полный; для каждой возвращённой очереди — `IWakeupSignal.Signal`. Пауза `PromoterInterval × (1 ± 0.2)`, по умолчанию 1 с. Адаптивный интервал по ближайшему `run_at` не делается: при 1 с выигрыша нет.
- **Sweeper:** `SweepExpiredLeasesAsync(1000)` (core §5.6), повтор, пока пакет полный. Пауза `SweeperInterval × (1 ± 0.2)`, по умолчанию 15 с.
- Ошибки — лог и следующий интервал.

### 6.4 Остановка (`PgBoltProcessingService.StopAsync`)

Координатор останавливает все серверы процесса одновременно; порядок остановки hosted services хоста (`ServicesStopConcurrently`) на это не влияет.

1. Для всех серверов сразу: сигнал остановки `Dispatcher` (новые dequeue не начинаются) и отмена shutdown-токена сервера — общего `CancellationTokenSource`, с которым связан токен каждого выполнения. Останавливается `ProcessingMaintenance`. `JobRunner`, стартовавший после отмены (диспетчер проверил `stopping` раньше сигнала), видит уже отменённый токен и возвращает задачу release с `ran = false`, не вызывая исполнитель; если отмена пришла между этой проверкой и вызовом, задача получает `OperationCanceledException` и уходит в release с `ran = true` (§5.1 п. 1, 4).
2. In-flight dequeue токеном остановки **не** отменяется (только своим таймаутом, §4.3): отмена после коммита statement'а оставила бы взятые строки незарегистрированными, и sweeper засчитал бы попытку. Взятые им задачи регистрируются и сразу отправляются как release с `ran = false` (§7.1), не запускаясь. Ожидание in-flight dequeue идёт параллельно с шагом 3.
3. Ожидание выполнений всех серверов параллельно, каждого — до `ShutdownTimeout` своего сервера от начала остановки. Не остановившиеся бросаются: их записи переводятся в `Removed` и удаляются из таблицы `LeaseKeeper` (§6.2), lease истечёт, sweeper засчитает попытку. Задача продолжает работать (прервать `Task` нельзя); исход, который она сдаст позже, отбрасывается (§6.1).
4. `CompletionSink` каждого сервера отправляет накопленные ack и оставшиеся исходы (включая release), с повтором по §6.1. После этого sink остановлен и новые исходы не принимает.
5. Остановка `LeaseKeeper` — только после шага 4: lease держатся, пока не отправлены исходы.
6. Удаление строк серверов (§7.2).
7. Остановка цикла обновления `QueueSettingsCache` — после `FlushAndStopAsync` серверов, то есть после завершения диспетчеров и их in-flight dequeue (часть 3b §6.1); ветка ошибки старта §4.4 п. 6 останавливает его вместе с остальным запущенным.

Каждый шаг ограничен токеном `StopAsync` хоста; при его срабатывании оставшиеся шаги с обращением к БД пропускаются (lease истекут сами): `CompletionSink` прерывает отправку (§6.1), удаление строк серверов не выполняется. Локальные циклы всё равно останавливаются — `CompletionSink`, `LeaseKeeper` и таймер предупреждений §5.1: иначе в процессе, который живёт дольше хоста (несколько хостов в процессе, тестовые хосты), heartbeat продолжал бы продлевать lease брошенных выполнений, и они не истекли бы.

## 7. Новый SQL

### 7.1 Release (graceful shutdown и незапущенные задачи)

Возвращает задачу в очередь без траты попытки; при запрошенной отмене финализирует её как Cancelled (инвариант core §4.1). Применяется только в двух случаях:
- `ran = true` — задача остановилась по shutdown-токену (он сработал первым, §5.2 п. 4);
- `ran = false` — задача не запускалась: взята после сигнала остановки (§6.4 п. 1–2) или в состоянии «heartbeat потерян» (§6.2).

Остановка по `HeartbeatLost` сюда не относится — это путь retry (§5.2).

```sql
WITH l AS MATERIALIZED (
    SELECT job_id, cancel_requested FROM {schema}.queue
    WHERE job_id = @id AND lease_id = @lease_id
    FOR UPDATE
),
r AS (
    UPDATE {schema}.queue q
    SET lease_owner = NULL, lease_id = NULL, lease_until = NULL, leased_at = NULL,
        attempt = q.attempt - 1, ready = true
    FROM l WHERE q.job_id = l.job_id AND NOT l.cancel_requested
    RETURNING q.job_id
),
c AS (
    DELETE FROM {schema}.queue q USING l
    WHERE q.job_id = l.job_id AND l.cancel_requested
    RETURNING q.job_id, q.attempt - CASE WHEN @ran THEN 0 ELSE 1 END AS attempt, q.leased_at
),
cj AS (
    UPDATE {schema}.jobs j SET state = 4, attempt = c.attempt,
                               started_at = CASE WHEN @ran THEN c.leased_at ELSE j.started_at END,
                               finished_at = now(), server_id = @server
    FROM c WHERE j.id = c.job_id AND j.id = @id
),
ev AS (
    INSERT INTO {schema}.job_events (job_id, at, kind, server_id, attempt, message)
    SELECT job_id, now(), @kind_cancelled, @server, attempt, @message FROM c
)
SELECT (SELECT count(*) FROM r) AS released, (SELECT count(*) FROM c) AS cancelled;
```

- Результат: `Released | Cancelled | LeaseLost` (обе колонки 0).
- Событие для release не пишется: это не ошибка задачи.
- `ready = true`: задача сразу доступна другому поду. Строка с `lease_owner IS NOT NULL` всегда `ready` (core §4.1), поэтому `run_at` не меняется.
- Ветка возврата всегда делает `attempt − 1`: инкремент dequeue не засчитывается ни для остановленной по shutdown, ни для незапускавшейся задачи.
- Ветка отмены пишет в `jobs.attempt` и `job_events.attempt` номер последней реально запускавшейся попытки: при `ran = true` — текущий `attempt` (попытка выполнялась и прервана), при `ran = false` — `attempt − 1` (попытки, взятой dequeue'ем, не было; может быть `0`, как у отмены невзятой задачи в core §5.7). `started_at` при `ran = false` не меняется.
- Блокирует одну строку, как fail (core §5.4); правило порядка захвата core §5.3 не затрагивается.

### 7.2 Регистрация и снятие сервера

```sql
INSERT INTO {schema}.servers (id, name, host, queues, capacity, started_at, heartbeat_at)
VALUES (@id, @name, @host, @queues, @capacity, now(), now())
ON CONFLICT (id) DO UPDATE
    SET name = EXCLUDED.name, host = EXCLUDED.host, queues = EXCLUDED.queues,
        capacity = EXCLUDED.capacity, heartbeat_at = now();          -- started_at не меняется

DELETE FROM {schema}.servers WHERE id = @id;
```

`host` — `Environment.MachineName`. Уборка строк упавших серверов — часть 2 (§5.6): удаляются только строки с устаревшим `heartbeat_at`; строку живого сервера восстанавливает его heartbeat (§6.2).

## 8. Изменения core

Реализуются в `PgBolt.Postgres`/`PgBolt.Abstractions` вместе с частью 3; тексты core §4.5, §5.5, §5.10, §6.3 при реализации приводятся в соответствие.

### 8.1 Heartbeat по списку lease (core §5.5)

```sql
WITH s AS (
    UPDATE {schema}.servers SET heartbeat_at = now() WHERE id = @server
    RETURNING 1
),
l AS MATERIALIZED (
    SELECT job_id FROM {schema}.queue
    WHERE job_id = ANY(@ids) AND lease_id = ANY(@lease_ids) AND lease_owner = @server
    ORDER BY job_id                                -- порядок захвата core §5.3 не меняется
    FOR UPDATE
),
u AS (
    UPDATE {schema}.queue q SET lease_until = now() + @lease
    FROM l WHERE q.job_id = l.job_id
    RETURNING q.job_id, q.lease_id, q.cancel_requested
)
SELECT EXISTS (SELECT 1 FROM s) AS server_present, u.job_id, u.lease_id, u.cancel_requested
FROM (VALUES (1)) AS one(x) LEFT JOIN u ON true;
```

- Сигнатура: `Task<HeartbeatResult> HeartbeatAsync(Guid serverId, IReadOnlyCollection<LeaseRef> leases, TimeSpan lease, CancellationToken ct)`; `HeartbeatResult(bool ServerPresent, IReadOnlyList<HeartbeatLease> Leases)` (часть 2 §9.2).
- Продлеваются только lease из списка; строки сервера вне списка истекают и уходят sweeper'у (§6.2). Без фильтра брошенная runtime строка продлевалась бы, пока жив под.
- Правило потери упрощается: lease из списка, отсутствующий в ответе, потерян. Отдельная проверка «dequeue завершился до отправки heartbeat» не нужна — в список попадают только зарегистрированные выполнения (§6.2).
- Условие по `job_id` даёт доступ по PK, как у ack; после ожидания блокировки READ COMMITTED перепроверяет `lease_id`, поэтому строка, освобождённая и взятая заново, не продлевается.
- Пустой список: обновляется только `servers.heartbeat_at`.

### 8.2 `IWakeupSignal`: подписка вместо ожидания (core §5.10)

```csharp
public interface IWakeupSignal
{
    void Signal(string queue);

    /// <summary>callback вызывается синхронно из Signal; должен быть дешёвым и не блокировать.</summary>
    IDisposable Subscribe(string queue, Action callback);
}
```

- `WaitAsync` удаляется: он не сообщает, какая очередь сработала, а `InProcessWakeupSignal` теряет сигнал без ожидающего (`TryRemove`).
- `InProcessWakeupSignal`: подписчики по очереди (copy-on-write массив), `Signal` вызывает их синхронно; исключение callback'а перехватывается и не доходит до вызывающего enqueue.
- Latch-семантику обеспечивает подписчик (событие `wake` диспетчера, §4.3); сигнал до подписки не нужен — первая итерация диспетчера опрашивает все очереди.
- **Breaking change** публичного API `PgBolt.Postgres`: `IWakeupSignal` регистрируется через `TryAddSingleton` (`PgBoltServiceCollectionExtensions`), поэтому пользовательская реализация (например, Redis pub/sub) перестанет компилироваться — ей нужно заменить `WaitAsync` на `Subscribe`. Отмечается в changelog; до 1.0 допустимо.
- Тесты: `WakeupSignalTests` переписываются на `Subscribe` (callback вызывается для своей очереди и не вызывается для чужой; `Dispose` отписывает; исключение callback'а не доходит до `Signal`; несколько подписчиков одной очереди); `RecordingWakeup` (`tests/PgBolt.Postgres.Tests/ClientTestSupport.cs`) реализует `Subscribe` вместо `WaitAsync`.

### 8.3 `PgBoltInitializer.Ready`

- `internal Task Ready` на `TaskCompletionSource` (`RunContinuationsAsynchronously`): успех — после проверки изоляции, миграций и партиций на сегодня (фоновое создание будущих партиций не ждётся); исключение — при падении `StartAsync`; отмена — при отмене его токена.

## 10. Тестирование

**Unit** (без PostgreSQL; `FakeTimeProvider`, фейковый store):
- `SlotAllocator`: строгий порядок; `Reserved` не отдаётся другим очередям; `MaxConcurrency` учитывает reserved и общие слоты; недобор очереди переходит к следующей в той же итерации; слот возвращается того же вида; очередь с `n = 0` не попадает в план; стратегия заменяема, её некорректный ответ и конец плана при готовой очереди со свободным слотом отклоняются (§4.2).
- Адаптивный polling и пробуждение: полный пакет → сразу; пусто → удвоение до `MaxPollInterval`; wakeup и освобождение слота сбрасывают `nextPoll`; сигнал, пришедший во время dequeue или до ожидания, не теряется; освобождение слота будит диспетчер без исключений; неожиданная ошибка итерации и отказ стратегии дают паузу, а не холостой цикл; сбой запуска выполнения откатывает регистрацию и слот (§4.3).
- Dequeue: таймаут `HeartbeatInterval` срабатывает при зависшем store; задачи dequeue, вернувшегося позже таймаута (store не соблюдает токен), не запускаются и уходят в release с `ran = false`, вернувшегося ровно в таймаут — запускаются; остановка не отменяет in-flight dequeue; задачи, полученные после сигнала остановки или в состоянии «heartbeat потерян», не запускаются и уходят в release с `ran = false`; `JobRunner`, стартовавший после отмены shutdown-токена, не вызывает исполнитель и отдаёт release с `ran = false`.
- Классификация исходов: каждая строка таблицы §5.2, включая первенство причин отмены; `Shutdown` + `OperationCanceledException` → release с `ran = true`; `HeartbeatLost` (в том числе с последовавшим shutdown) → retry с тратой попытки, при `attempt = max_attempts` — окончательный fail; исключение, отличное от `OperationCanceledException`, после shutdown.
- `RetryPolicy`: ряд задержек, потолок, границы jitter, отсутствие переполнения при больших `attempt`; `retry_delays` задачи важнее политики, последний элемент повторяется, пустой массив = политика; `null` → окончательный fail; NoExecutor передаёт `JobExecutorNotFoundException`.
- `LeaseKeeper`: heartbeat отправляет только lease таблицы; выполнение, зарегистрированное после снимка, не проверяется; потерянное отменяется и его исход снимается; потеря при исходе в полёте не отменяет исход; гонка CAS `OutcomePending → OutcomeInFlight` с обработкой ответа heartbeat — ровно один победитель; `validUntil` = `fetchStartedAt + LeaseDuration` при регистрации и растёт до `sentAt + LeaseDuration` только для lease из ответа; проверка срока lease отменяет выполнение в `validUntil − HeartbeatInterval`, даже если вызов heartbeat висит; вызов heartbeat прерывается через `HeartbeatInterval / 2`.
- Сценарии сбоя heartbeat (`FakeTimeProvider`): задача, чей dequeue длился ≈ `HeartbeatInterval` и зарегистрирован после снимка успешного heartbeat, отменяется в `t0 + LeaseDuration − HeartbeatInterval`, а не на `HeartbeatInterval` позже; dequeue, начатый до сбоя и завершившийся после входа в «heartbeat потерян», не запускает задачи и отдаёт release с `ran = false`; выполнение, стартовавшее во время сбоя, отменяется по своему `validUntil`; в «heartbeat потерян» — пауза выборки, исходы не отбрасываются; снятие после успеха.
- `CompletionSink`: сброс ack по размеру и по окну; повтор любой ошибки с backoff; `LeaseLost` после неоднозначной ошибки; исчерпание бюджета `LeaseDuration` удаляет выполнение из таблицы и из следующего heartbeat; выполнение не покидает таблицу до завершения отправки; исход выполнения, брошенного при остановке или с подтверждённо потерянным lease, и исход после остановки sink отбрасываются.
- Координатор: один hosted service при нескольких `AddPgBoltServer`; остановка отменяет shutdown-токены всех серверов до ожидания любого из них; предупреждение §4.4 п. 5 считается по процессу.
- `PgBoltInitializer.Ready`: успех, исключение и отмена `StartAsync`.
- `InProcessWakeupSignal.Subscribe` и обновлённый `RecordingWakeup` (§8.2).
- Фильтры: порядок (глобальные → серверные), короткое замыкание, исключение фильтра = исключение задачи, scoped-резолв.
- Валидация опций (§3.1, §3.2, §3.3), включая `MaxConcurrency = 0`, `MaxConcurrency < Reserved` и верхние границы длительностей; урезание `[Job(TimeoutSeconds)]` до предела таймера с предупреждением (§5.1); диагностики генератора BOLT007/BOLT008 (§3.5).

**Интеграционные** (Testcontainers, дважды: напрямую и через PgBouncer transaction mode):
- Enqueue → выполнение → Succeeded; пакетный ack под нагрузкой.
- Retry с задержкой → повтор после promotion; исчерпание → Failed; `JobAbortedException` и битые аргументы → сразу Failed.
- Отмена выполняющейся задачи доходит через heartbeat → Cancelled.
- Таймаут → retry с сообщением timeout; задача без таймаута выполняется дольше любых значений по умолчанию.
- NoExecutor → retry, после исчерпания — Failed; предупреждение на старте.
- Shutdown: задача, остановившаяся по токену, возвращается с прежним `attempt` и сразу берётся другим сервером; игнорирующая токен после истечения lease засчитывается sweeper'ом; release задачи с `cancel_requested` → Cancelled с `attempt` прерванной попытки; строка `servers` удалена.
- Shutdown во время dequeue (задержка ответа через прокси; чтобы момент «statement закоммичен, ответ задержан» был детерминирован, dequeue сначала паркуется на блокировке таблицы `queue`): взятые задачи возвращаются с прежним `attempt`; взятая задача с `cancel_requested` → Cancelled с `attempt` без несуществующей попытки.
- Release SQL (§7.1): обе ветки при `ran = true`/`false`, fencing по `lease_id` (чужой lease → `LeaseLost`).
- Несколько виртуальных серверов в одном процессе с долгими задачами: при остановке ни один сервер не теряет попытки; promoter и sweeper — по одному на процесс.
- Потеря lease: sweeper забирает задачу у сервера с остановленным heartbeat → выполнение отменено, его ack не проходит, задача выполнена другим сервером.
- Сиротская строка: строка с `lease_owner` сервера и неизвестным runtime `lease_id` не продлевается heartbeat'ом, истекает и обрабатывается sweeper'ом.
- Сбой исхода: fail/ack падают (например, нет партиции `job_events`) дольше бюджета → lease истекает, sweeper засчитывает попытку; задача не висит в Processing.
- Кратковременная недоступность БД (короче `LeaseDuration`): после восстановления исходы доставлены, lease известных выполнений продлены, ничего не висит в Processing; при недоступности дольше `LeaseDuration − HeartbeatInterval` (пауза прокси) выполнения отменены до истечения lease и попытка засчитана. Выполнения, взятые dequeue'ем, завершившимся во время сбоя heartbeat, проверяются отдельным тестом с выборочным сбоем (блокировка строки `servers` роняет только heartbeat): при полной паузе прокси ответ dequeue не приходит в пределах его таймаута `HeartbeatInterval`, а «heartbeat потерян» наступает только через `LeaseDuration − HeartbeatInterval ≥ 2 × HeartbeatInterval`.
- Задача, исчерпывающая пул `NpgsqlDataSource` так, что heartbeat не получает соединение: отменяется по `HeartbeatLost`, каждая остановка тратит попытку, после `max_attempts` — `Failed`.
- Инвариант: N серверов × M задач без искусственных сбоев — каждая задача выполнена ровно один раз, ничего не потеряно.

**Нагрузочный smoke** (SLO — часть 7): один процесс, 100k коротких задач; throughput не деградирует со временем (окно замера — 10 с при обработке ≥ 40 с, иначе четверть длительности), число соединений ограничено пулом. Только напрямую: через PgBouncer `pg_stat_activity` не показывает соединения процесса.
