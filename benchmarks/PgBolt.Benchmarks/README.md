# PgBolt.Benchmarks: lock против lock-free в синхронизации рантайма

Микробенчмарки (BenchmarkDotNet 0.15.8) пяти мест синхронизации в `src/PgBolt.Server/Runtime`. Каждое место сравнивается
так: точная копия текущего ядра синхронизации против lock-free варианта. БД, сеть и PgBouncer заменены заглушками.
Продуктовый код не менялся. Internal-типы не открывались через InternalsVisibleTo: ядро скопировано в `Copies/`, в
шапке каждой копии указаны исходный файл и коммит; `MonoClock` (без синхронизации) компилируется из продукта.

Это не тестовый проект: `IsTestProject=false`, тестового SDK в нём нет, поэтому `dotnet test PgBolt.slnx` его не запускает.

## Запуск

```bash
# только стресс-проверки инвариантов (код возврата 1 при провале); можно сузить: --verify event|sink|slots|table|deadlines
dotnet run -c Release --project benchmarks/PgBolt.Benchmarks -- --verify

# все бенчмарки (перед ними Main сам прогоняет --verify и при провале не запускает замеры); ~20 мин на M4 Pro
dotnet run -c Release --project benchmarks/PgBolt.Benchmarks -- --filter '*'

# одно место
dotnet run -c Release --project benchmarks/PgBolt.Benchmarks -- --filter '*SlotAllocator*'

# перцентили задержки ping-pong (отдельно от BDN)
dotnet run -c Release --project benchmarks/PgBolt.Benchmarks -- --latency

# проверить, что все случаи запускаются (Job.Dry вместо основного Job), ~15 с
PGBOLT_BENCH_DRY=1 dotnet run -c Release --project benchmarks/PgBolt.Benchmarks -- --skip-verify --filter '*'
```

Отчёты BDN сохраняются локально в `BenchmarkDotNet.Artifacts/`. Команда `--latency` печатает путь к своему отчёту.

## Методика

- Job `Concurrent`: 2 процесса × (4 прогрева + 12 замеров по ~250 мс), `UnrollFactor=1`. Разные процессы по-разному
  размещают потоки на P- и E-ядрах, поэтому процессов два. Добавлены `MemoryDiagnoser` (аллокации всего процесса на
  операцию), `ThreadingDiagnoser` (work items пула, Lock Contentions), а также колонки Median, P95, Min и Max.
- Конкурентные сценарии устроены одинаково. Выделенные потоки создаются в `GlobalSetup` (`WorkerPool`); `Barrier`
  стартует их одновременно, каждый делает фиксированную долю операций. `OperationsPerInvoke` равен общему числу операций,
  так что **Mean — время на одну операцию в сумме по всем потокам**, а пропускная способность = 1/Mean. Число потоков
  задаётся через `[Params]`, базовая линия (Ratio = 1) — текущий lock-вариант.
- Перед замерами каждый прототип проходит стресс-проверку ключевого инварианта (`Verification/Verifier.cs`), а вместе с
  ним и копии текущего кода.

**Все 18 проверок инвариантов прошли за 95 с**. Наивный вариант ArmAtMost без эпохи
проверка ловит, как и должна.

## Результаты

Apple M4 Pro (8P+4E, 12 ядер), macOS 27.0, .NET 10.0.9 Arm64. Время — на одну операцию в сумме по всем потокам, Δ —
изменение времени относительно lock (минус — быстрее; ×N — во сколько раз выше пропускная способность). Аллокации —
байт на операцию по всему процессу.

### 1. AsyncAutoResetEvent — CAS (уже в HEAD) против lock (aaf1738)

| Сценарий | Потоки | lock | CAS | Δ | Аллокации lock → CAS |
|---|---:|---:|---:|---:|---|
| Set при одном ожидающем | 1 | 8.97 ns | 0.78 ns | −91 % (×11) | 2 B → 0 |
| | 4 | 8.84 ns | 0.37 ns | −96 % (×24) | 0 → 0 |
| | 8 | 11.11 ns | 0.35 ns | −97 % (×32) | 0 → 0 |
| | 12 | 11.07 ns | 0.48 ns | −96 % (×23) | 0 → 0 |
| Ping-pong, круг (BDN, async) | 2 | 2.09 µs (медиана 1.92) | 1.51 µs (медиана 1.44) | −27 % (RatioSD 0.12) | 915 B → 606 B (−34 %) |
| Холостой `WaitAsync(0)` | 1 | 6.8 ns | 14.1 ns | **+108 %** | 0 → 0 |
| Холостой `WaitAsync(1 мс)` | 1 | 1.322 ms | 1.321 ms | 0 % (время — гранулярность таймера) | 1383 B → 1255 B (−9 %) |

Почти все Set здесь попадают в уже взведённый латч. У CAS это одно чтение без записи, у lock — вход в lock и выход из
него, поэтому разница в разы. Ping-pong в отдельном прогоне (`--latency`, блокирующее ожидание, 3×200 000 кругов): среднее 2.55–3.10 мкс у lock против 2.52–2.76 мкс у CAS,
p50 2.67–3.08 против 2.62–2.88, p99 3.71–9.21 против 3.92–6.21. Разброс между прогонами больше разницы между вариантами,
явного выигрыша по хвостам нет. `WaitAsync(0)` у CAS медленнее на ~7 нс. Предположение, не проверялось: дело в
`Interlocked.CompareExchange` над ссылочным полем (helper с GC write barrier на Arm64) против `lock` с полем `bool`.

**Вывод: оставить CAS (он уже в HEAD).** Выигрыш на Set и ping-pong измерим, аллокаций меньше, корректность
подтверждена. Регрессия на таймауте 0 в абсолютных цифрах ничтожна.

### 2. CompletionSink.Complete(ack)

Основной прогон, 4 варианта.

| Потоки | (а) lock | (б) дешёвый lock | (в) lock-free | (в′) lock-free, триггер `==` | Аллокации а / б / в / в′ |
|---:|---:|---:|---:|---:|---|
| 1 | 35.1 ns | 34.7 ns (−1 %) | 39.9 ns (+14 %, бимодально: медиана 47.6) | 24.4 ns (−30 %) | 45 / 45 / 13 / 13 B |
| 4 | 48.9 ns | 44.1 ns (−8 %) | 139.1 ns (+190 %, ×0.34) | 124.8 ns (+160 %) | 45 / 45 / 20 / 19 B |
| 8 | 49.8 ns | 46.1 ns (−6 %) | 271.4 ns (+451 %, ×0.18) | 263.4 ns (+435 %) | 45 / 45 / 38 / 52 B |
| 12 | 52.1 ns | 49.7 ns (−4 %) | 448.0 ns (+765 %, ×0.12) | 438.6 ns (+747 %) | 45 / 45 / 38 / 35 B |

Первый прогон, 3 варианта:
(б) против (а) дал −2 / +17 / +11 / +5 %, (в) против (а) дал +24 / +224 / +502 / +847 % на 1 / 4 / 8 / 12 потоках.

- **Lock-free проигрывает в 2.6–8.7 раза уже с 4 потоков.** Lock на 12 потоках даёт ~19 млн Complete/с, lock-free —
  ~2.2 млн/с. Сначала подозревался шторм неудачных CAS на флаге дренажёра, поэтому добавлен вариант (в′); он не помог
  (−2…−10 % к (в) на 4–12 потоках). Значит, дорого само по себе: два спорных атомарных RMW на операцию (`ConcurrentQueue.Enqueue` и
  `Interlocked.Increment` счётчика) на разных кэш-линиях. У `System.Threading.Lock` под нагрузкой одна атомарная
  операция и короткая секция, которую держатель выполняет серией (это гипотеза, профилем не подтверждалась). Без
  конкуренции (1 поток) (в′) быстрее lock на 30 % и аллоцирует меньше (13 B против 45 B), но это не тот режим, ради
  которого стоит что-то менять.
- **Дешёвый lock — в пределах шума.** Знак разницы меняется между прогонами (+17 % против −8 % на 4 потоках при RatioSD до 0.2).
- Найдено при проверке: если `Complete` идут непрерывно, lock-free `StopAsync` фактически ждёт, пока поток Complete
  иссякнет. В тесте Stop он принял ~389 тыс. из 400 тыс. записей, а lock-версия завершалась после ~69 тыс. Lock-версия
  успевает увидеть пустой буфер под lock'ом, lock-free почти всегда находит новую отправку.

**Вывод: оставить lock.** Lock-free медленнее под конкуренцией и намного сложнее: Деккер на `_stopped`, вечный флаг
дренажёра после остановки, протокол `_timerArmed`, окно, отсчитываемое от последнего срабатывания таймера. Есть и
поведенческий риск со Stop. Дешёвый lock выигрыша не даёт, а добавляет риск: задача регистрируется под lock, но
запускается после него.

### 3. SlotAllocator — Take + Release

| Потоки (1 диспетчер + R) | lock | Interlocked | Δ | Аллокации |
|---:|---:|---:|---:|---|
| 2 (R=1) | 76.1 ns | 71.7 ns | −5 % (в пределах RatioSD 0.09) | 0 / 0 |
| 4 (R=3) | 198.5 ns | 78.7 ns | −60 % (×2.5) | 0 / 0 |
| 8 (R=7) | 469.9 ns | 174.2 ns | −63 % (×2.7) | 0 / 0 |
| 12 (R=11) | 561.5 ns | 206.5 ns | −63 % (×2.7) | 0 / 0 |

Выигрыш устойчивый и большой в относительных цифрах, но в абсолютных это 0.2–0.56 мкс на взятую задачу. При 10 000
задач/с это 2–6 мс процессорного времени в секунду, на фоне выполнения задач и обращения к БД.

**Вывод: оставить lock (или заменять только при профиле, показывающем конкуренцию).** Есть конкретные риски замены.
(1) Перестаёт быть атомарным снимок счётчиков для `Plan`/`ISharedPoolDistribution`. Проверка контракта стратегии в
`NextEntry` («план кончился, а у готовой очереди есть свободный слот» → `InvalidOperationException`) начнёт ложно
срабатывать: `Release` между ответом стратегии и проверкой увеличивает `Available`. (2) Однопоточность `Take`
становится неявным инвариантом, который нужно охранять. (3) Двойной `Release` обнаруживается только после `Decrement`.
В микробенчмарке Plan не участвует.

### 4. ExecutionTable.Snapshot

Время одного снимка или минимума:

| Записей | Фон. писатели | Snapshot (текущий) | без Count | Δ | Аллокации | Минимум: Snapshot+цикл | по перечислению | Δ | Аллокации |
|---:|---:|---:|---:|---:|---|---:|---:|---:|---|
| 100 | 0 | 732 ns | 409 ns | −44 % | 856 → 2192 B | 996 ns | 303 ns | −70 % | 896 B → 0 |
| 100 | 4 | 4.00 µs | 0.85 µs | −79 % | (*) | 4.96 µs | 1.28 µs | −74 % | (*) |

в строках с писателями не относится к снимку.

Add+Remove (одна пара) из N потоков, пока отдельный поток непрерывно снимает снимки. Δ — к варианту с текущим Snapshot:

|---:|---:|---:|---:|---:|---:|
| 100 | 1 | 32.8 ns | 162.2 ns | 48.2 ns (−70 %) | 40.7 ns (−75 %) |
| 100 | 4 | 45.1 ns | 142.4 ns | 65.7 ns (−54 %) | 66.0 ns (−54 %) |
| 100 | 8 | 67.8 ns | 141.1 ns | 69.6 ns (−51 %) | 63.4 ns (−55 %) |
| 100 | 12 | 49.3 ns | 138.1 ns | 58.4 ns (−58 %) | 69.0 ns (−50 %, RatioSD 0.10) |
| 10 000 | 1 | 31.1 ns | 45.8 ns | 54.1 ns (+18 %) | 34.5 ns (−25 %) |
| 10 000 | 4 | 20.9 ns | 42.5 ns | 35.3 ns (−17 %) | 23.6 ns (−44 %) |
| 10 000 | 8 | 19.1 ns | 58.4 ns | 33.8 ns (−42 %) | 23.4 ns (−60 %) |
| 10 000 | 12 | 19.6 ns | 47.0 ns | 36.9 ns (−21 %) | 22.5 ns (−52 %) |

Аллокации на пару: 56 B без снимков (узел словаря), 71–235 B с текущим Snapshot, 112–303 B без Count, 56–59 B с минимумом.

`Count` у `ConcurrentDictionary` захватывает все полосы и тормозит и сам снимок, и писателей. На малой таблице его
удаление даёт −44…−79 % времени снимка и в 2–3 раза ускоряет писателей при непрерывных снимках. На 10 000 записей
List без ёмкости растёт удвоением (в 3 раза больше аллокаций, LOH), и снимок без Count становится медленнее на 10–44 %.
Минимум рубежа по перечислению выигрывает везде (−39…−74 %), не аллоцирует и почти не мешает писателям.

**Вывод: заменить в `RearmDeadlineTimer` Snapshot+цикл на минимум прямо по перечислению.** Выигрыш однозначный, правка
локальная, риска нет: семантика та же, потому что перечисление и раньше шло без lock'ов, а Count не давал атомарного
снимка. Для heartbeat-`Snapshot()` однозначного ответа нет: без Count лучше при типичном числе выполнений (≈ Workers,
десятки–сотни), хуже при 10 000. Компромисс — ёмкость из известной оценки (например, Workers) вместо `Count`, но он
**не измерялся**. В абсолютных цифрах это микросекунды раз в HeartbeatInterval, так что приоритет низкий.

### 5. LeaseKeeper.ArmAtMost — эпоха (seqlock) против lock

Register + Unregister, одна пара:

| Rearm | Рубежи | lock | epoch | Δ | Аллокации |
|---|---|---:|---:|---:|---|
| нет | растут | 54.0 ns | 51.2 ns | −5 % | 208 / 208 B |
| нет | убывают | 55.3 ns | 54.0 ns | −2 % | 208 / 208 B |
| ~1 мс | растут | 54.3 ns | 51.9 ns | −4 % | 208 / 208 B |
| ~1 мс | убывают | 57.1 ns | 57.0 ns | 0 % | 208 / 208 B |
| ~10 мкс | растут | 83.2 ns | 79.0 ns | −5 % | 219 / 219 B |
| ~10 мкс | убывают | 87.3 ns | 86.2 ns | −1 % | 220 / 220 B |

Регистрацию почти целиком занимают `new Execution` (с CTS), `Add` и `Remove` в словаре. Эпоха экономит неконкурентный
вход в lock и выход из него: 0–4 нс на регистрацию.

**Вывод: оставить lock.** Выигрыш 0–5 % (единицы наносекунд) не оправдывает протокол: seqlock, ожидание нечётной
эпохи, повторный `Change` при пересечении с Rearm. Наивная версия без эпохи **некорректна** (проверка её ловит), а
корректная требует аккуратного доказательства. Наблюдение из проверки: два потока, делающие Rearm без пауз, через
несправедливый lock практически остановили регистрацию — первая версия проверки не завершила 300 000 Register за
7 минут. В продукте Rearm редок, это патология стресс-теста, а не реальный сценарий. Тем не менее lock здесь не
гарантирует прогресс.

## Ограничения

- **macOS и P/E-ядра.** Привязать потоки к ядрам нельзя, планировщик раскладывает их по 8 P- и 4 E-ядрам, а QoS не
  управляется. BDN не смог поднять приоритет процесса («Permission denied»). Отсюда бимодальность: например, (в) на
  1 потоке — Mean 39.9 при медиане 47.6 нс. Перенос на Linux x64 может изменить соотношения, особенно у атомарных
  операций под конкуренцией.
- **Переподписка.** На 12 рабочих потоков приходятся ещё ожидающий, диспетчер или поток снимков, то есть 13 активных
  потоков на 12 ядер.
- **Шум.** RatioSD до 0.2 (CompletionSink на 4 потоках). Между двумя прогонами знак разницы (б) против (а) сменился,
  поэтому разницы меньше ~15 % здесь не различимы. Ping-pong в BDN (асинхронное продолжение) и в `--latency`
  (блокирующее ожидание) измеряет разные механизмы, и абсолютные числа у них разные.
- **Микробенчмарк без БД.** Отправка ack, Store и таймер LeaseKeeper — заглушки. Абсолютная цена всех вариантов —
  наносекунды и микросекунды на задачу, а обращение к БД — миллисекунды. «−60 %» в относительных цифрах не значит
  заметного эффекта в продукте.
- **Худшие случаи.** Снимок в бенчмарке записи идёт непрерывно (в продукте — раз в HeartbeatInterval и по таймеру),
  Rearm раз в 10 мкс; эти сценарии искусственно усиливают конкуренцию.
- **Allocated** — аллокации всего процесса. В строках с фоновыми писателями туда входят и их аллокации.
- **Lock Contentions** почти везде ~0: `System.Threading.Lock` в основном справляется спином, а счётчик учитывает только
  ожидания с блокировкой. Нулевой счётчик не значит, что конкуренции не было.
- Копии ядра урезаны до горячего пути (что опущено — указано в шапке каждого файла `Copies/`). Lock-free прототип
  CompletionSink поддерживает только ack.
